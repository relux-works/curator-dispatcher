## 1. Purpose

The dispatcher is where a launch becomes an execution. It takes from today's `task-board spawn` the part that starts executions and keeps their records, and makes it a module that works with or without a board:

1. it accepts a request from a person, an orchestrator, the board or a tool, authenticates the caller by its OS account and its request signature, and checks the caller's grant;
2. it checks and reserves this machine's capacity;
3. it provisions an agent: an OS account through swarma-user-manager, a binding in swarma-credential-broker with a leaf grant narrowed for the agent and the caller's authorization recorded as a dependency;
4. it starts the agent's executor under that account through the helper's launcher, tracks the execution, and stops it through the helper when asked;
5. it cleans up per policy, and after any crash reconciles its records with the helper, the broker and the process evidence, including reverse inventory after state loss, before admitting new work under the confinement rules of §7.1.

Without a dispatcher, Curator can still launch directly, without accounting; with one, everybody launches through it. The board and its toolchain are optional clients, never dependencies of this module.

### 1.1 Non-goals

- It does not choose roles, models or efforts, and does not compose plans; a plan is opaque bytes with a digest.
- It does not hold credentials and does not run as root.
- With a session host present, it does not hold processes (§12).
- It does not decide when board work is accepted; the board's own completion barrier stays with the board (§14).

### 1.2 Names

| Name | Meaning |
|---|---|
| dispatcher | this component, under its service account `swarma-dispatcher` (names follow the platform root `/opt/swarma`) |
| caller | the principal that sends a request: a person's account, an orchestrator agent, the board's runner, the session host |
| agent allocation | one provisioned agent account generation and what the dispatcher keeps about it (`agent/1`) |
| execution | one start of one plan under one allocation (`run/1`) |
| host launcher | `swarma-user-launcher`, the privileged transition into an agent account (helper repository) |
| executor | `curator-run` from `curator-agent-launcher`, in its versioned, narrow one-shot exec mode under the agent account: verifies and executes a plan composed by the caller, prepares the working directory, leases its credential and execs the harness; it never composes or resolves profiles in this mode (§5.3). Long-lived sessions use `swarma-session-runner` under the agent account instead (SH2+, §12). |
| supervisor | the dispatcher-owned process that holds one execution (inside the daemon) |

## 3. Identities and authority

### 3.1 The dispatcher's account

The dispatcher runs as the unprivileged service account `swarma-dispatcher`, created by the helper for the installer. Only this account is a **dispatcher** in the helper policy and in the broker, so the root transitions and bindings are reachable only through it. The dispatcher is a trusted principal for its scope: a compromised dispatcher can sign leaves within its own grant and administer the agents it created, but cannot exceed the broker-verified root bounds or obtain a general root shell from the helper's closed operations.

### 3.2 Callers

- The caller is the kernel-reported peer UID on `dispatch/1`, with the broker's connection rules (§4.1): protected socket directory and endpoint, client verification of the server UID, bounded authenticated connections and descriptor-inheritance/passing restrictions. Caller-to-service sudo authority is absent; dispatcher-to-root helper and launcher authority remains (§11).
- Principals follow broker §4.2: managed callers by `(uid, generation)` with the helper ledger showing the generation `active` (re-checked for every operation, every queued start and every reconciliation); unmanaged callers pinned by UID and directory identity. An unreadable or invalid ledger refuses; a recycled UID never inherits old allocations or executions.

**Operator custody (F-23 / R-OPERATOR; owner-decided 2026-10-12).** The dedicated account `swarma-operator` MUST NOT host a harness session. It, rather than the person's interactive account, is the configured broker operator and account owner, the user manager's `operator` UID, and the holder of operator signing authority, including the broker v0 root and signed operator records. Operator binaries and configuration are protected from agent writes. Interactive agent sessions have no operator authority. The mandatory read-only account `swarma-observer` admits dispatcher state reads without confirmation (§8.1), including status, grants, accounts and bindings as represented by the dispatcher; it confers no mutation or direct helper/broker operator authority. Read representations not already specified would need publication (§16).

The main operator path uses an **operator device key**, hardware-backed and presence-gated, in the phone's Secure Enclave or StrongBox. The key MUST NOT leave the phone and is usable only after biometric confirmation. The phone app connects by SSH over the tailnet into `swarma-operator`, with login by that key only and no shell: a forced narrow **operator command** accepts operator acts only. Before signing each act, the app shows its exact content (who, which actions, until when); the machine verifies the signature against the pinned phone key. Each operator act is a signed operator record bound to that one act's canonical content; its signature cannot be reused for another act. The operator device key is an admitted signer for `swarma-dispatcher team/1` and standing-retirement records. The operator command binary name/wire format, signature domain and canonical bytes remain unpublished (§16); this does not change the published caller-request or broker signature algorithms or formats.

The terminal fallback uses password-authenticated `sudo` into `swarma-operator`, with no `NOPASSWD` and no cached ticket (`timestamp_timeout=0`), and produces records under that account's signing authority. It works without a phone. Widening acts require authentication plus confirmation of the exact act content: grant issue, subscription enrolment, `team/1`, standing retirement or re-creation, explicit home retention, maintenance stop authority and standing re-grants. The operator CLI MUST refuse these acts from inside an agent session; dispatcher admission MUST refuse operator records originating there, even with an otherwise valid signature. Narrowing acts (revocation or disabling an account) require authentication only; phone revocation takes a single biometric confirmation. Reads use `swarma-observer` without confirmation. `NOPASSWD` is reserved for the dispatcher service account's helper and launcher rules (§11). Already-authorised bounded service effects retain their existing authority; they cannot mint a new operator record or confirmation. Origin/confirmation evidence, terminal signing format and key enrolment/rotation/loss recovery would need publication (§16).

### 3.3 Caller keys and request signatures

- The dispatcher's configuration (owned by its account, written by the operator through the installer) maps each **principal** to its **caller keys** (Ed25519). An orchestrator's caller key is generation-bound. `register_key` records its public key separately from caller-authority activation; the requester signs its delegation only after registration (§5.2). Operator-enrolled orchestrators are supported in the initial slice with generation-bound keys and valid caller chains installed through operator configuration; this does not require the unpublished pre-key exception. Recursive provisioning is refused until its bootstrap is published and qualified.
- Except for the narrow pre-key `register_key` exception below, every mutating `dispatch-op/1` request carries `auth: { key, sig }`: an Ed25519 signature by a caller key over the domain tag `swarma-dispatcher request/1`, a newline and the CCJ-1 bytes of the request without `auth`. The key must be associated with the authenticated principal (`caller_key_not_associated`), and the leaf of the caller's grant chain must have that key as its subject (`grant_subject_mismatch`).
- **Wire naming (D-WIRE-NAMES).** Versioned wire identifiers use the repository name: `swarma-<component> <object>/<n>`. The signed request domain above is exactly `swarma-dispatcher request/1`; the request-signature newline does not apply to the effect hash (§4.5). Broker signed domains are `swarma-credential-broker grant/1` and `swarma-credential-broker revocation/1`. Nothing has shipped, so these clean names require no migration or legacy-domain acceptance. This decision supersedes the contract table's W2 retention baseline; it does not publish the helper v2 signature grammar (§16). The existing dispatcher transport/schema labels `dispatch-op/1` and `dispatch/1` remain distinct from the signed domain.
- A valid chain presented without the matching principal and signature is refused; a copied chain is useless to another caller.
- **Pre-key registration exception (R-DELEG).** Only the authenticated allocation's own active `(uid, generation)`, already selected for orchestrator enrollment by valid requester/operator authority, may register its first caller key. This exception permits key registration with proof of possession of that key, never `provision`, `start` or spawn authority. It does not use a nonexistent previously registered key. The dispatcher durably binds the enrollment intent, generation, key and registration replay evidence before acknowledgement. An exact replay returns the same registration; a changed key or enrollment intent refuses, a reused UID cannot replay a former generation's registration, and unavailable replay evidence keeps registration closed. The proof-of-possession domain, canonical bytes, freshness window and replay identity are unpublished (§16); the exception is disabled until these are published and qualified.
- **Rotation.** A new key requires proof of possession and authorization by the currently enrolled key within its current authority, or explicit operator recovery if that key is unavailable. Rotation is journaled and serialized with activation: the old key loses its association, stale registration replays cannot restore it, and a replacement delegation to the new subject must be verified before caller authority is active. Registration never silently rotates a key or transfers authority. The rotation signature/replay format and operator recovery authorization would need publication (§16).

### 3.4 Grants and their constructible shapes

- **Action vocabulary:** `agent.spawn` (may ask the dispatcher to provision and start agents within the grant's accounts, harnesses and profiles) and `credential.lease` (may lease those accounts). Unknown actions refuse (`grant_unsupported`).
- **Caller chain:** the caller's leaf grant names the caller key, allows `agent.spawn` and `credential.lease`, and has remaining depth ≥ 1. It chains to a configured root under the broker's verifier (broker §6.2), at most 4 envelopes.
- **Dispatcher chain:** the dispatcher's own grant names the dispatcher key, allows `credential.lease`, has depth ≥ 1, and is at most 3 envelopes long, so an agent leaf can be appended within the 4-envelope bound. The installer refuses to configure a dispatcher chain outside this shape.
- **Agent leaf:** signed by the dispatcher key under its own chain; subject `agent:<generation>`, depth 0, action `credential.lease` only; accounts, harnesses, profiles and window are the intersection of the request, the caller's grant and the dispatcher's grant. A request whose intersection is empty or whose leaf could not be constructed is refused before any account is created (`grant_unconstructible`).
- **Caller dependency:** the binding carries the caller's chain and the exact intersection (broker §7, revision 0.3). The broker verifies both chains, separately, at bind, lease and every renewal, against the current revocation state: revoking the caller's grant or key stops new leases and renewals for every agent provisioned under it immediately. Tokens already delivered remain valid until they expire or are revoked at the vendor.
- **Orchestrator delegation preflight (R-DELEG).** For requester C to delegate spawn authority to O, C's chain must leave depth for O's `agent.spawn` and `credential.lease` leaf: C's leaf depth ≥ 2, O's depth strictly smaller and ≥ 1, and C's chain plus O's envelope ≤ 4. Each edge uses the parent subject as issuer. The dispatcher chain remains lease-only and never substitutes for C's caller ancestry. Insufficient depth or chain length refuses before account creation.
- **Revocation verdict (R-VERDICT).** At prepare, dequeue (when enabled) and every start, the configured dispatcher calls broker `broker/1` method `revocation.check` with the exact caller and dispatcher chains being checked and context `prepare`, `dequeue` or `start`. The broker answers `not_revoked`, `revoked` or `unavailable`, together with its revocation sequence at the check. Only `not_revoked` passes this check; `revoked` and `unavailable` refuse before new effects. Fenced broker restore answers `unavailable`. The verdict is point-in-time evidence, never a grant or a future-start permit; no cached verdict substitutes for a new admission check. Exact encoding and refusal-code mappings would need publication (§16).
- **Delayed and recovered work** (a queued request, a start after `provision`, a resumed cleanup that would start anything) re-checks the caller principal, request signature and validity window, caller chain and a fresh `revocation.check` verdict before acting. The broker's final bind, lease and renewal checks remain mandatory; an earlier verdict cannot prevent later revocation.

**Session lifecycle authorisation (R-SESSION).** An owner's admitted `start` with the session-runner executor may explicitly authorise successor executions for one logical session, on the same allocation/generation and the stored plan verbatim. Its member format is unpublished (§16). It is consent distinct from the fresh checks above: a one-start request without it admits no successor. The owner's chain remains the binding's caller dependency; the host acquires no caller chain or node-wide spawn/lease grant. Every successor rechecks the stored owner principal/signature, current chain/window, allocation lifetime and a fresh `revocation.check` with context `start`. Retirement of a one-shot orchestrator makes its owned sessions non-restartable. Ordinary work also needs a cumulative or first-start-anchored restart budget (successor count or total runtime anchored at first start) in that authorisation; successors cannot reset runtime windows or extend allocation lifetime. Standing executions retain no runtime limit (§12).

**Credential-authority renewal (R-REBIND).** E-rebind re-signs the agent leaf under current caller and dispatcher chains and asks the broker for a **binding replacement** on the same `(uid, generation)`, retaining a removal tombstone for the old binding. It has its own durable effect ID, fresh `revocation.check` with context `prepare` and broker `effect.observe`; the account is not re-created. The renewing principal must already sit in the chain: `swarma-operator` renews dispatcher authority and standing roles through a signed team description or standing re-grant using §3.2's phone or terminal path, with exact-content confirmation and refusal from agent sessions; the owner supplies a fresh signed request for an ordinary kept allocation; an orchestrator's requester supplies a fresh requester-signed delegation from its authenticated connection. The dispatcher's own signature is never renewal consent. The fresh renewal request/consent is retained as its own immutable input linked to the allocation; it never edits the original admission input. The new leaf intersects the current chains with the originally admitted request and never widens accounts, harnesses or profiles; wider scope requires new `provision` admission. Expired authority needs explicit renewal by its authorised principal; revoked envelopes/keys need a new explicit operator decision, never sweep re-issuance.

**Machine-owned network binding (R-NETBIND).** The root-owned, agent-readable policy beside user-manager configuration (user manager §8 owns its location) maps the admitted Curator profile identity and lock digest to exactly one network profile ref/digest; `direct` is allowed only by that policy. No grant dimension is added. At `prepare`, resolve and pin the binding in `input/1`. Caller `network` text must match it and differing text refuses before effects; caller home configuration is never authority for the binding. Under helper v1, `fw.apply` checks that the trusted listener actually serves the policy whose digest was pinned. Policy/catalog drift refuses rather than silently substituting another profile. An authorised machine-policy narrowing on an existing allocation pins the narrowed policy's ref/digest in a distinct linked record/effect, with fresh authority where required; it never rewrites immutable `input/1` or silently substitutes a new policy in the original admitted effect. Retry/recovery of each effect uses its own pin; policy/catalog drift against that pin still refuses. The linked narrowing record/effect and its authorisation/pin encoding would need publication (§16). Helper kernel state flush and proxy-side session drop/recheck must both be confirmed. Reload/port reuse cannot silently change an already-bound listener's policy. The trigger/transport and canonical profile-to-served-allowlist digest relation and listener/service-generation lifetime binding remain publication gates (§16); v0 is declared/cooperative only.

**Authority time (R-TIME).** The dispatcher keeps a durable time **watermark**. Detect clock steps and validate time confidence before evaluating authority or advancing it. Expiry is checked at `max(now, watermark)` and `not_before` at `min(now, watermark)`, so a clock step can only narrow authority. The watermark never advances on untrusted time; reset is an explicit operator act preserving genuinely expired authority. A single platform time-confidence policy applies: compare wall and monotonic deltas within a boot, hold on backward steps or forward steps beyond its tolerance, and establish confidence after boot by authenticated sync or operator confirmation. Untrusted time closes new admission and renewal, and holds time-based evidence reclamation; authorized explicit stops and operator retirement stay available. The tolerance, confidence evidence and durable reset/elapsed formats would need publication (§16).

### 3.5 Quotas

Configuration sets, per caller and in total: live allocations, concurrent executions, and, for ordinary allocations and their executions, the maximum allocation lifetime and the maximum execution runtime. Requests beyond the applicable quotas are refused (`quota_exceeded`) — a permanent refusal, never a queueable condition.

Defaults (owner decision 2026-10-10), all configurable:

| Limit | Per caller | Per node |
|---|---:|---:|
| concurrent executions | 2 | 6 |
| live allocations | 4 | 16 |
| allocation lifetime (one-shot and ordinary kept allocations) | default 24 h, maximum 7 days | — |
| execution runtime (all executions other than those of standing allocations) | default 4 h, maximum 12 h | — |

Standing allocations cover the standing team's orchestrator and fixed roles, including other orchestrators and standing agents. They have no `expires_at` and no lifetime quota. Only the operator may retire or re-create them, with a signed record (§§4.3, 5.4–5.5); the sweep never expires them (§7.2). Per the owner decision of 2026-10-12 (§16, question 6), their executions MUST NOT acquire a `max_runtime` quota or runtime deadline, in either supervisor or session-host backends. The sweep MUST NOT stop them for runtime. They end only by an explicit stop (`cancel`/stop through `exec.stop`), operator action, their own exit or an incident hard stop (§5.3). Live-allocation and concurrency quotas still apply. Every other execution retains the 4 h default and 12 h maximum.

No allocation expiry is permission for immediate destruction: expiry-driven retirement also requires §5.4's trusted-time and monotonic elapsed gate. Allocation lifetime is distinct from credential-authority horizon (§§4.3, 7.2).

The per-caller execution limit matches the host's existing rule of two runs per orchestrator.

## 4. Records and state

Figures M-DP2: [execution states](../diagrams/run-states.puml) and [allocation and claim states](../diagrams/agent-claim-states.puml); M-DP3: [storage ownership and durable ordering](../diagrams/storage-layout.puml).

### 4.1 State directory

The state lives under `/opt/swarma/services/swarma-dispatcher/state` (mode 0700): the immutable inputs, the record files, the effect table, the journal, the index, the claims, the dispatcher key and the lock. The state-transition lock covers journal and record transitions only. **Never hold its state lock across a synchronous call to another platform service (R-LOCK).** Under the lock, fix immutable canonical arguments/provenance and journal the intent with a durable per-record in-flight marker; release it, make the call, then reacquire it to validate and record the result. Per-record serialization prevents competing effects; unrelated records and recovery controls stay available. In-flight work and outbound I/O have bounded concurrency and deadlines; a stalled record must not exhaust the control workers. Singleton/process-ownership locks, including the launcher's generation exclusion, have separate lifetimes and are not mechanically released by this rule.

Every call is bound to the record/version, daemon-instance epoch and, for the host backend, controller epoch. The call-issue transition under the lock is the cancellation boundary: a cancellation recorded before it prevents issue; after it, record cancel requested on the in-flight marker, retain claims and resolve the same effect/receipt before stopping. Cancellation and fence withdrawal record intent promptly; they cannot assert absence of possibly executed work. Revalidate every late result against current versions/fences under the lock: stale completions may resolve historical evidence but cannot reopen admission/delivery or resurrect a cancelled start. Supervisor writes require the current durable daemon-instance epoch (R-FATE); a surviving writer from a replaced daemon cannot write, and is never adopted. These marker/epoch encodings are unpublished (§16).

The dispatcher's wait/lock graph is: state lock → local journal/record I/O only; unlocked call worker → user manager/launcher or broker; host's unlocked call worker → dispatcher. No state-transition lock is held on any cross-service wait, and no cross-service callback waits for that lock while its caller holds another service's state lock. Per-record waiters release the global lock. The graph must remain acyclic; receiver ownership locks are governed by their own published graphs. Record files are replaced atomically (temporary file, flush, rename, directory flush); the journal is appended and flushed before any external effect; on start-up the journal is replayed over the record files, so a crash between the two leaves no ambiguity.

### 4.2 Immutable input `input/1`

Before a request is accepted, its caller principal and root `request_id`, its canonical bytes, the decoded plan bytes, the full caller chain and the computed digests are written once and never changed. Every later step, including a queued start or a recovery, reads from this object. It also retains the admitted session lifecycle authorisation, when present, and the machine-owned network binding's pinned ref/digest and Curator profile identity/lock digest; their record/member formats remain unpublished (§16). The session record retains the same authorisation. Neither a successor nor a retry accepts substituted plan bytes, wider scope or a caller-selected network binding.

### 4.3 Agent allocation `agent/1`

```
{ v: 1, kind: "agent/1",
  agent_id:   "AG-<yymmdd>-<random>",
  owner:      principal reference, request input id,
  generation, uid, username, label,
  capabilities: ["orchestrator"]?,          // §5.2
  binding_id, leaf_grant_id, caller_chain_ids,
  caller_key?:  registered orchestrator key (§3.3),
  state:      "provisioning" | "idle" | "running" | "retiring" | "removed" | "failed",
  active_execution: run_id | null,          // at most one
  expires_at?: allocation expiry (absent for standing allocations),
  cleanup: { home: "delete" },             // ordinary retirement; explicit retention is operator-only
  created_at, updated_at }
```

`agent/1` MUST retain a designation that marks an allocation as standing, tied to the operator-signed team description (§5.5). A standing allocation MUST NOT carry `expires_at` or acquire a lifetime quota. The designation's wire encoding and the signed retirement/re-creation record format are specified-but-unpublished; no member name or value for them is defined here (§16). Ordinary allocations retain their expiry and §3.5 lifetime bounds. Only the operator may retire or re-create a standing allocation, with a signed record; a caller's `agent.spawn` is insufficient.

Account generations are fresh random 128-bit values allocated by the user manager (R-GEN; user manager §4.1), never dispatcher counters or reconstructed from a label/UID. Random generation uniqueness does not authenticate restored state (§11.1).

Each allocation retains its credential-authority horizon: the earliest end of the current caller/dispatcher chains, leaf and binding. Standing lifetime does not extend that horizon. E-rebind replaces its binding/leaf references only after confirmed broker evidence, retaining old-binding removal obligations and tombstones through recovery; the record encoding would need publication (§16).

When keeper integration is activated, the allocation must retain the registration reference and the one-shot flag recorded at registration (§14); the exact keeper API/schema is an activation prerequisite.

### 4.4 Execution `run/1`

```
{ v: 1, kind: "run/1",
  run_id:     "RUN-<yymmdd>-<random>",
  agent_id, owner, input id, plan_digest, executor,
  claim:      { execution_id, epoch, state: "claimed" | "launching" | "started" | "stopping" | "absent" },
  receipt:    { pid, start_time, boot_id } | null,   // from the launcher, §6
  state:      "accepted" | "queued" | "starting" | "running" | "stopping" | "cleaning"
            | "done" | "failed" | "cancelled" | "expired",
  outcome:    { kind: "exit" | "failed" | "cancelled" | "expired" | "lost", exit_code?, signal?, stage?, code? } | null,
  deadline?:  { max_runtime, ends_at },     // ordinary executions only; absent for standing
  parent, board_ref (opaque, kept whole),
  created_at, updated_at }
```

An execution of a standing allocation MUST NOT carry `deadline`, `max_runtime` or `ends_at` as a runtime limit. An ordinary execution retains its runtime deadline under §3.5. Absence is the standing contract; no sentinel duration, null deadline or additional wire member is defined.

`run/1` records a `host_stop` as host-requested, distinct from owner `cancel`; the representation is unpublished, so no outcome value/member is added. Each physical successor has its own execution claim and distinct effects, and the session permit's `(logical_session_id, op_id)` replay relation is durable (§12).

### 4.5 Effect ids and the effect table

| Identifier | Meaning and owner |
|---|---|
| root `request_id` + caller principal | caller-scoped request correlation and repeat lookup; kept in immutable input, journal and audit metadata, not reused as every receiver's idempotency key |
| effect id | dispatcher-derived idempotency key for one downstream operation; retries reuse it, different effects do not |
| `agent_id` | allocation handle (`agent/1`), distinct from account generation |
| `run_id` | dispatcher execution handle (`run/1`), distinct from board run/attempt handles |
| `execution_id` | execution claim and launcher/stop receipt identity; its exact construction from `run_id` is not frozen here |
| account `generation`, broker `binding_id` | never-reused account generation and binding identity; UID or label alone is not authority |
| broker `launch_id` | correlation only (plan digest or run ID), never authorization |
| claim `epoch`, backend `controller_epoch`, `op_id` | execution claim epoch, host controller fence epoch and backend operation identity; none is an account generation (§12) |

Every downstream call has an **effect id**: the first 32 hex characters of SHA-256 over the domain tag `swarma-dispatcher effect/1` and the CCJ-1 bytes of `{ caller principal, request_id, record id, component, operation, attempt }`. Its inputs are journaled before the call; a retry of the same effect reuses its id; create, bind, launch, stop, unbind, retire and E-rebind use distinct ids. Every receiver I/O step uses §4.1's journal/in-flight → unlock/call → lock/revalidate ordering; a journaled verdict is never cached admission authority. The symbolic E-rebind denotes the broker binding replacement, whose operation encoding remains unpublished; it is not a new wire field. The effect table records, per effect: id, component, operation, intent time, result (`ok` with the returned identity, `refused` with its code, or `unknown`), and the last observation. The root caller correlation is retained alongside the effect's input reference for tracing. Two callers using the same `request_id` never collide downstream. No newline is added between the effect domain and its CCJ-1 bytes.

For one `dispatch` root request `R` by principal `C`, the following are symbolic IDs derived by the formula above, not literal IDs or new downstream members:

| Call | Receiver idempotency key | Root correlation kept by dispatcher |
|---|---|---|
| helper `user.create` | `request_id: E-create` | `(C, R)` |
| broker `bind` | `request_id: E-bind` | `(C, R)` |
| broker binding replacement (operation encoding unpublished) | `request_id: E-rebind` | `(C, R)` |
| launcher `launch.start` | `request_id: E-launch` | `(C, R)` |
| helper `exec.stop` | `request_id: E-stop` | `(C, R)` |
| broker `unbind` | `request_id: E-unbind` | `(C, R)` |
| helper `user.retire` | `request_id: E-retire` | `(C, R)` |

Each `E-*` uses its record, component, operation and journaled attempt; a retry replays the same intent and ID. The root `R` is never substituted for an `E-*`. Separate `provision` and `start` requests have separate root request IDs; their effects remain correlated to their own originating request and the shared allocation.

Receiver-owned read-only `effect.observe` is published by `helper-op/1` and `broker/1`. The dispatcher asks with the original effect's `request_id`, operation and digest of canonical arguments; the lookup never performs a mutation. Only the original receiver caller principal (here, the dispatcher) or an operator may observe; the receiver serializes the read with its journal. It remains usable for reconciliation after the initiating caller/grant expires and grants no fresh mutation authority. R-OUTCOME is owned by the receivers: the user manager's §§4.6–4.7 and §7 publish the outcome tables for create, launch, stop and retire; broker §§7.2 and 13.2 publish bind/unbind and binding-replacement outcomes. The dispatcher follows those per-operation tables and their existing six R-OBS states rather than inferring completion from a refusal string. Terminal mutation replay returns the recorded result and current target state. Unfinished admitted work maps to `pending` handling, never a terminal `refused` in the dispatcher effect table; transport uncertainty remains unknown/unavailable. A pre-admission rejection records no receiver intent; an authority-creating retry requires fresh permission, expiry and revocation checks. An admitted stop or unbind may continue to narrow authority after the initiating grant lapses, using the original ID and identical canonical arguments; changed arguments remain a conflict. `exec.stop` with `processes_remain` continues under E-stop and revalidates generation/current-execution fencing on every continuation. A completed stop replays without signalling, and never signals a later execution. Broker unbind uses the matching removal/tombstone observation; retention and exact encoding would need joint publication (§16). Missing or expired evidence is `unavailable`, never absence.

### 4.6 Observations

Reconciliation and recovery classify every observation of the helper ledger, the broker binding, the claim and the process evidence as **known present**, **known absent**, **unknown** (unreadable, timed out) or **contradictory**. Unknown and contradictory observations never authorise forward execution, a second launch or a successful cleanup; the record stays where it is and the observation is retried.

R-OBS maps the receiver's six states exactly:

| Receiver state | Dispatcher observation class |
|---|---|
| `recorded`, with recorded result and current target state | known present or known absent according to the current state |
| `pending` | unknown |
| `rolled_back` | known absent for that effect only |
| `not_recorded`, with complete authoritative evidence it was never recorded | known absent for that effect only |
| `unavailable`, including missing, expired or unreadable evidence | unknown |
| `contradictory` | contradictory |

`rolled_back` and `not_recorded` never authorize an automatic new create. Absence for an effect does not establish absence of another effect or of every process. A partial list, refused observation, timeout or unreadable evidence cannot establish absence, release capacity or satisfy cleanup. Process absence and launch/stop receipts remain separately required.

R-OUTCOME's receiver tables distinguish unfinished accepted work from pre-admission rejection before this mapping is applied (§4.5); no seventh observation state is introduced. Uncertainty is confined to the affected records only when complete durable intent, identities and quota/capacity reservations bound every possible result. Unknown receiver-assigned identities can still be confined by those complete intents and claims. Unknown is never absence. If identity scope, accounting, shared authority or state integrity is unbounded, node-wide forward admission stays closed (§7.1). Restored observations require independent coverage; a restored snapshot cannot prove its own completeness (§11.1).

## 5. Lifecycle

Figure M-DP1: [provision, launch, refusal and recovery sequence](../diagrams/dispatch-lifecycle.puml).

### 5.1 Allocation

`provision` (or the first half of `dispatch`):

1. **prepare** — schema, principal, signature, chains, delegation depth preflight when applicable, quotas, constructibility, plan digest, machine-owned network binding resolution/pinning (§3.4) and fresh `revocation.check` with context `prepare`; write `input/1`. Refusal ends here with no effect.
2. **capacity** — take an owned claim (§9) or refuse initially; queue only when that capability is enabled, with a fresh `dequeue` check before any effect.
3. **provision** — helper `user.create { kind: agent, label, request_id: <effect id> }` → generation; (helper v1) `fw.apply` with the admitted binding ref/digest, served-policy verification and drift refusal; v0 records declared networking only; sign the leaf; broker `bind { uid, generation, lease chain, caller chain, intersection, request_id: <effect id> }`. The allocation becomes `idle`.

On failure an ordinary allocation goes to `retiring`: unbind (if bound) and `user.retire` (if created), each as its own effect, retried until confirmed; the allocation becomes `failed` only after those effects and any applicable identity cleanup (§14) are confirmed.

For a standing allocation, provisioning failure does not authorise automatic retirement or re-creation. Keep it pending for reconciliation or an operator-signed decision (§§5.4–5.5, 7.1); unknown observations never permit a duplicate effect.

### 5.2 Orchestrator allocations

The home-generated caller key is distinct from a keeper-retained identity key; broker software roots are a third key class. Keeper adoption requires the versioned broker migration adapter (§14), not relabelling a caller key as a keeper identity.

**Requester-signed delegation (R-DELEG).** Requester C signs O's caller delegation, narrowed from C's own grant, after O's public key has been registered under O's active generation (§3.3). C is the issuer and O's registered key is the subject; the dispatcher D verifies and records this chain and never signs O's caller delegation. D continues to sign only its separate credential-lease agent leaf (§3.4). Descendants retain C in their ordinary caller chain, so ancestor revocation remains an ordinary verifier/broker dependency check.

Registration is separate from activating caller authority. Before provisioning, preflight remaining depth and the four-envelope bound (§3.4). At activation, recheck C's authenticated principal, request signature, delegation issuer/parent-subject continuity, O's generation/key association, attenuated actions/scope, depth, chain length, validity window and a fresh `revocation.check` with context `prepare`. A missing C signature, unavailable requester or missing/unavailable evidence leaves enrollment pending with no spawn authority. O cannot obtain implicit authority from its UID, registration, capability designation or the dispatcher's signature. Rotation needs a newly valid delegation to the replacement key.

The pre-key registration exception, replay and rotation rules are in §3.3; their wire format and the authority-install transaction remain unpublished (§16). Recursive orchestrator provisioning MUST refuse until this bootstrap is jointly published and qualified. Direct worker launches and operator-enrolled orchestrators form the initial slice. Operator enrollment does not waive registration or valid caller-chain requirements; no first-start bypass grants spawn authority.

An orchestrator composes its children's plans on the caller side, under its own agent account, using its own Curator configuration in its home. The child's `curator-run` only verifies the caller-composed plan before executing it (§5.3); it does not compose or resolve profiles. Which profiles and environments the orchestrator may read and use for its children, and how its narrowed grant constrains them, are unspecified and remain an open question (§16).

A renewed requester-signed delegation names exactly which existing descendant allocations it reauthorises. Each receives E-rebind with that new chain and retained ancestry; a new delegation does not silently rewrite descendants' bindings (§3.4).

**Cross-account workspace rule (F-16).** A child in another isolated account gets a standalone repository under its own home, with its own `.git`, common directory, refs, index, configuration and hooks; it is never a linked `git worktree`. Materialize the admitted exact base and approved content with freshly defined local configuration, excluding the parent's `.git` backlink, executable local configuration/hooks and credential helpers. Copy/reflink optimizations must preserve private writable administration; mutable hard-linked metadata is forbidden. Linked worktrees within one account, including today's board workflow, remain permitted. Any immutable read-only object sharing would need bounded source authorization, provenance/access and retention rules. Source/result transfer across private homes must use an approved repository/artifact path with a published owner and authorization before workspace-capable cross-account activation; no relaxed home permissions or recursive privileged chown compensates for a missing transfer contract (§§14, 16). This rule does not claim that code/results are secret-free.

### 5.3 Execution

`start` (or the second half of `dispatch`), on an `idle` allocation owned by the caller:

1. re-check the caller's authority and a fresh `revocation.check` with context `start` before any launch effect and, for an ordinary allocation, its lifetime and §3.5 runtime quota; take a capacity claim for one execution. A standing execution has no `max_runtime` quota or runtime deadline; an ordinary execution retains its runtime deadline;
2. **claim** — under the lock, write an execution claim `{ execution_id, epoch }` and mark the allocation `running`; only one claim per allocation (`agent_busy`);
3. **supervisor** — the daemon starts the supervisor; it registers its own process identity and acknowledges durably before anything else;
4. **launch** — the supervisor calls the launcher (`launch.start { request_id: <launch effect id>, generation, execution_id, epoch, executor, plan }`); the launcher writes a **start receipt** for that execution (pid, start time, boot id) while still root, before clearing groups, setting GID/UID and exec (helper §7); the user manager §7 owns the descriptor lifecycle (R-FD3): scrub untrusted inherited descriptors first, retain the generation lock through the root receipt and completed UID/GID transition, retain the verified executable handle until exec, and release internal handles at last use/close-on-exec and on every failure. The executor receives only 0–2 and read-only FD3 with completely staged, bounded immutable plan bytes; the per-platform staging mechanism remains a publication gate, and any pipe would need qualified capacity/feeder/deadline/cleanup ordering. No broker or root handle is inherited; the supervisor records the receipt;
5. **running** — `curator-run` in its narrow exec mode verifies the caller-composed plan, prepares its working directory in the agent's home, resolves the protected credential binding, opens its own broker connection, leases its credential and execs the harness. For an ordinary execution, `max_runtime` expiry leads to **stopping**. A standing execution has no runtime deadline and ends only by an explicit stop (`cancel`/stop through `exec.stop`), operator action, its own exit or an incident hard stop; the sweep never stops it for runtime. Exit, explicit stop, operator action or an incident hard stop leads to **stopping**, with absence confirmed in step 6;
6. **stopping** — the supervisor (or recovery) calls helper `exec.stop { request_id: <stop effect id>, generation, execution_id }`, which uses the user manager's single termination scope (§4.7, shared with retirement): TERM/grace/KILL every process of the generation's UID, stop its per-user service domain where present, and verify account-wide absence over the qualified quiet period. The receipt authenticates the current execution; its session or wall-clock start window never limits the signalled/verified set. The latest-receipt fence prevents an old stop from signalling a later sequential execution; completed stops replay without signalling. A termination receipt requires confirmed account-wide absence;
7. **finish** — record the outcome; the allocation returns to `idle` (ordinary kept or standing agents) or proceeds to `retiring` (ordinary `dispatch`, an expired ordinary allocation, or operator-signed retirement of a standing allocation).

**One-shot intake gate (D-EXECUTOR).** `curator-run` under the agent account is the first broker consumer. The board runner and session host ask the dispatcher; neither embeds a broker client. This mode never composes or resolves profiles and has no network access except to the broker; harness egress is governed separately by the admitted network policy. It shares one launch library with `swarma-session-runner`. A dedicated entry such as `curator-run exec --plan-fd N` illustrates the mode, not a published CLI grammar. The launcher owner (R-LR1) publishes the versioned Decision 0021 amendment and intake contract (immutable plan verification, FD transport, credential injection capability, signals, exit/receipts and typed refusals). This launch path stays disabled until that contract is published and qualified; the older interactive scope is not evidence of one-shot support. A separate minimal executor binary is a later option, not the current target.

The managed plan records the resolved PATH and covers it with its digest (D-PATH): protected launch tool directory (CIP-0007), then admitted base PATH in its existing order, then one protected manager dispatcher directory. Project commands pass that dispatcher's checks; a repository `.agents/bin` is never executed in a managed launch. The exact plan schema is owned with the intake contract.

A cancel is serialised with the claim and per-record in-flight marker (§4.1): before call issue, it marks the claim `absent` and the launcher is never called; during the launch, the supervisor waits for the receipt or the launcher's refusal and then stops; after the launch, it stops. A request never issues a second launch for an execution whose state is unknown.

### 5.4 Retirement and expiry

`retire` of an ordinary allocation, an expired ordinary allocation, or a finished one-shot `dispatch`: unbind, then `user.retire` under the user manager's delete-at-retirement rule (§4.4.1), each a confirmed effect. The user manager quiesces the account, cleans declared keys and deletes its home. There is no archive-by-default policy. Any retained retirement export is limited to service-generated metadata in a closed schema with no agent-controlled strings, names, links or bodies. Code/results follow their separate git/acceptance policy, which does not prove secret-free content.

**Expiry destruction (R-TIME).** Before any expiry-driven retirement/home deletion, including retirement because a caller/credential window expired, require both expiry at `max(now, watermark)` under established time confidence and durable accumulated boot-inclusive monotonic elapsed time of at least the allocation lifetime, counted from activation. Use `CLOCK_BOOTTIME` on Linux or continuous time on macOS; accumulate at each sweep with boot identity because the clock resets on reboot. Downtime is not counted and may only delay destruction. Unknown elapsed/confidence evidence holds destructive expiry; a forward wall-clock step alone cannot delete a home. Expired authority remains unusable while destruction waits. This gate does not prevent an explicit authorised stop or operator retirement. Broker expiry-driven binding removal has the same two gates under its own R-TIME contract.

**Direct operator retirement (F-12).** The user manager retires locally without a broker call or broker role. Ordinary dispatcher cleanup keeps confirmed unbind-before-retire. If an operator directly retires the account while broker cleanup is unavailable/refused/unconfirmed, retain an explicit durable broker-cleanup obligation at the dispatcher/operator boundary and report it in status/reconciliation; ledger retirement is never an unbind receipt. Use the existing dispatcher/operator broker API and E-unbind/`effect.observe` with retained tombstones to resolve it. The irreversible retiring generation never returns active, and UID reuse inherits no old binding. Dispatcher records do not claim cleanup success until broker evidence confirms it (§7.1); the obligation/reporting format would need publication (§16).

Keeping a home is a separate explicit operator retention operation owned by the user manager, under `swarma-operator` authority and §3.2's phone or terminal path with exact-content confirmation and agent-session refusal; it must state plainly that the home's confidentiality is not guaranteed. Dispatcher cleanup has no retention authority and admits `delete` only (§4.3); the retention operation's unpublished format would need publication by the user manager (§16).

With keeper integration active, the dispatcher then revokes an identity only if its registration recorded it as one-shot (§14), as a separate, confirmed effect after account retirement. Standing identities are left to the operator. The allocation becomes `removed` only after its applicable cleanup effects are confirmed; executions become terminal only after their stop is confirmed and their allocation's cleanup obligations are recorded. The daemon's internal sweep (§7.2) owns ordinary allocation lifetimes while no request is running.

Standing allocations do not expire and are not retired on execution exit, provisioning failure or loss of caller authority. Only `swarma-operator` may retire or re-create them, with a signed operator record through §3.2's phone path (operator device key, biometric confirmation and exact content shown) or password-authenticated terminal fallback. Records originating inside an agent session MUST be refused. Once such retirement is authorized, the same confirmed cleanup effects apply; reconciliation may retry those authorized effects but cannot initiate retirement on its own. Account retirement never revokes a standing identity (§14). Re-creation is an operator decision, not an automatic recovery from an absent account or binding. The signed-record format remains unpublished (§16).

### 5.5 Bring up team (specified-but-unpublished)

Companion figure: [operator-signed team bring-up and per-role reconciliation](../diagrams/bring-up-team.puml).

The dispatcher has a `swarma-operator`-only bring-up-team operation from a signed operator record describing the standing team, through §3.2's phone path or terminal fallback. Its request object is named **`swarma-dispatcher team/1`** under D-WIRE-NAMES. It is specified-but-unpublished; it is not an added `dispatch-op/1` value. The description lists the standing roles, each with only the following specified fields:

| Field | Meaning |
|---|---|
| `label` | the standing role's label |
| `profile` | the role's profile |
| `harness` | the role's harness |
| `accounts` | the role's accounts |
| `capabilities` | the role's capabilities |

Only authenticated `swarma-operator` authority with a valid signed description and exact-content confirmation may invoke it. On the main path the operator device key signs on the phone after the app shows the content and biometric confirmation; the machine verifies against the pinned phone key. The terminal fallback authenticates with a password and confirms the content (§3.2). A record originating inside an agent session MUST be refused. A caller with `agent.spawn`, including an orchestrator allocation, has no bring-up-team authority. The signature grammar, remaining envelope/record fields, role matching, change handling and transport are unspecified (§16); this section does not invent them or new refusal codes.

From the description, the dispatcher creates or reconciles one standing allocation per role, idempotently, with one logical bring-up effect per role: repeating bring-up or recovering it must not create a second allocation or duplicate a role's already-recorded effect. Provisioning uses the usual distinct, journaled effect IDs for create and bind (§4.5), reusing each ID on retry, and the existing provisioning/idle/running/retiring states and known-present/known-absent/unknown/contradictory observations (§§4.3, 4.6, 7.1). An existing allocation is reconciled, not automatically replaced; running allocations are not relaunched. An unknown or contradictory effect remains pending until observed. Retirement or re-creation always needs the operator's signed record (§5.4). Bring-up allocates roles; execution remains a separate start (§5.3).

Team renewal uses E-rebind on existing allocations with a fresh standing re-grant signed under `swarma-operator` authority via §3.2's phone or terminal path; re-grants require authentication, exact-content confirmation and agent-session refusal. Bring-up replay alone is not a fresh renewal request and never re-creates an account (§3.4). Renew-ahead requires a person before the credential horizon, or a pre-authorised bounded non-widening re-grant within an existing published delegation. No such automatic standing re-grant delegation is published here; without supplied valid authority the sweep parks/refuses forward work, never infers an infinite re-grant (§§7.2, 16).

## 6. Holding and stopping

- **Supervisor.** The daemon owns the per-execution supervisor under `swarma-dispatcher`: new session, no controlling terminal, caller descriptors closed, bounded private logs of the executor's output in dispatcher state, durable registration before launch, and start/termination receipts recorded. User manager §7 owns the process **fate table** (R-FATE) beside R-FD3: one row per dispatcher daemon, supervisor, execution root/descendants, broker vendor-refresh child and session-host service, with unit/kill domain, stop/crash/restart fate, promised survival, death observation and maintenance affected set per platform/unit configuration. Dispatcher and host backends reference that table, not deployment defaults. Supervisor backend daemon loss follows the explicit `lost`/confirmed-stop path; there is no live supervisor adoption or second launch. Every supervisor write checks the durable daemon-instance epoch; an old surviving supervisor is fenced from journal/log/record writes. Reconcile its historical receipt/effect and stop it as required (§7); no extra wire epoch field is defined here.
- **Stop.** The only stop is the helper's `exec.stop`, authorized for the dispatcher's own generations; ordinary ephemeral executions may also end through `user.retire`, which stops the account's processes before removal. Operator maintenance authority is explicit (§§8.1, 11). Stop and retirement share the user manager §4.7 account-wide scope and latest-receipt fence (§5.3). `idle` requires no account process; persistence-denial and quiet-period evidence are user-manager qualification prerequisites. Concurrent executions per generation would need exact per-execution containment before activation and must never fall back to session-only termination. Platform services and service managers end executions only through `exec.stop`, retirement or operator emergency stop; OS failures such as OOM are observed as `lost`, never successful cleanup. Qualification distinguishes caller disconnect/death, daemon death, executor ignoring SIGTERM and descendants escaping the session; a client connection is never the execution's lifetime authority.

## 7. Reconciliation and the sweep

### 7.1 Reconciliation

Companion figure: [state-by-state reconciliation](../diagrams/reconcile.puml).

Runs at daemon start before forward readiness, periodically inside the daemon, and on `reconcile`. Establish exclusive ownership, compatible schema, journal replay and valid authentication/indexes before serving the recovery/control surface. Status/list, receiver observation, reconcile and already-authorised current-execution-bound stops remain reachable without a fresh launch grant when their particular evidence is sound. Classify every non-terminal record before forward admission. Retain unresolved records' generation/allocation, quota and capacity reservations; reject their forward effects. Unrelated work may proceed only if complete accounting and durable intent/claims demonstrably confine every possible unresolved result. Unbounded shared-state integrity, identity scope, accounting or authority keeps node-wide forward admission closed; maintenance, restore fencing and the fail-closed hold gate remain global barriers. Calls use §4.1's in-flight marker and unlocked I/O pattern, including observations and the sweep. For every allocation and execution that is not terminal, it compares the journal and effect table with the observations (§4.6), state by state:

| State | Observation | Action |
|---|---|---|
| provisioning | create effect unknown | call helper `effect.observe` with original effect ID/operation/digest; apply §4.6; no automatic new create |
| provisioning | account present, bind effect unknown | call broker `effect.observe`; absence is effect-scoped only; resume only the same admitted bind effect with fresh `prepare` authority/verdict checks, never infer authority for a new effect; otherwise retire only an ordinary allocation under §5.4 (expiry requires its elapsed gate) or keep standing pending |
| idle | binding known absent, ordinary allocation not expired or standing allocation | reconcile original bind/unbind observations; a new bind requires explicit fresh authority and `prepare` verdict, never automatic creation from effect absence; if authority is gone, retire only an ordinary allocation under §5.4 (expiry requires its elapsed gate); standing stays pending |
| running, claim `claimed` | supervisor registration conclusively absent | mark the claim `absent`; no launch happens later |
| running, claim `launching` | receipt unknown | keep waiting for the receipt or the launcher's answer; never relaunch |
| running, `started` | supervisor known absent | `exec.stop`, then record `lost` |
| stopping | termination receipt missing / unfinished admitted stop | continue `exec.stop` under the same E-stop and identical canonical arguments; current-execution fence and account-wide absence remain mandatory |
| any record | supervisor survives a replaced daemon | reject its writes by daemon-instance epoch; reconcile historical receipt/effect and confirmed stop; never adopt it |
| existing allocation | credential authority approaches lapse / needs explicit renewal | E-rebind only with §3.4 authorised current chains and fresh `prepare` verdict; observe old removal tombstone and replacement; never re-create account |
| any record | direct operator retirement but broker cleanup unconfirmed | retain/report durable E-unbind obligation; local retirement is not broker absence |
| restored/lost state | receiver object has no dispatcher record | reverse-inventory orphan; retain identity and conservative accounting for operator decision (§11.1), never automatic adoption/deletion |
| retiring / cleaning | effects pending | repeat them; terminal only when all are confirmed |

Reconciliation uses `effect.observe` rather than mutation solely to discover state: `recorded` maps by current target state; `rolled_back`/`not_recorded` are known absent for that effect only and never trigger automatic new create; `pending`/`unavailable` remain unknown; `contradictory` stays contradictory. Follow receiver-owned R-OUTCOME tables (§4.5) for create/launch/stop/retire and bind/unbind/replacement. Observe helper create/retire and broker bind/unbind/replacement, including retained removal/tombstone evidence. Launch/stop use qualified receipt and process evidence; observations do not waive confirmed process absence. After caller/grant expiry, read-only observation can resolve prior effects without renewing authority. Any forward admission requires fresh §3.4 checks; missing evidence keeps claims held.

Reconciliation of a standing allocation never initiates retirement or re-creation without the operator's signed record, including on a provisioning failure or known-absent account. It may resume already-authorised effects; unknown and contradictory observations remain pending. The absence of allocation expiry does not waive fresh authority checks.

Helper retirement/recovery follows its bounded, dependency-based work contract (F-25; user manager §§4.4–4.6, 6–7). Serialized deletion batches yield its existing shared lock; an unrelated safely classified retirement need not finish before a stop/observation/launch on another generation. The dispatcher continues the original E-retire through cleanup/sweep retries, treats unfinished batches as `pending` under R-OUTCOME, retains UID/quota reservations and never declares `removed` before full deletion/account cleanup confirmation. Shared corruption or unbounded accounting still closes admission. This gives no new cleanup authority to the metadata-only daily root timer and promises no bound on a stuck kernel/storage device.

### 7.2 The sweep

The daemon runs an internal sweep every minute: reconciliation, ordinary allocation lifetimes, claim maintenance and log rotation. There is no external sweep timer or public sweep operation; caller `reconcile` remains scoped by §8.1. The sweep never expires standing allocations: they have neither `expires_at` nor a lifetime quota. It MUST NOT stop their executions for runtime, because they carry no `max_runtime` quota or runtime deadline. Ordinary executions retain §3.5's 4 h default and 12 h maximum; the sweep stops an ordinary execution whose runtime deadline has elapsed through confirmed `exec.stop` (§§5.3, 6). It reconciles standing allocations' authorized effects/executions and maintains claims and logs. Expiry-driven destructive cleanup follows §5.4's trusted-time and boot-inclusive monotonic elapsed gate. Persist elapsed/time evidence and classify clock incidents before authority evaluation or watermark advance. The sweep performs authorised renew-ahead E-rebind before the earliest credential window ends, only with consent and current renewed chains already supplied by §3.4's authorised principal; it cannot mint grants or reissue revoked/expired authority autonomously. Status reports each allocation's credential-authority horizon and the dispatcher grant's `--until` as the node-wide horizon, including approaching lapse; the status encoding remains unpublished. Unbind ends the old binding's running leases: until a fenced fresh-lease handoff is published and qualified for a holder, use explicit park/restart keeping the account; no seamless env-channel or app-server continuation is promised. Tokens already delivered keep their vendor lifetime. A sweep over many records uses bounded per-record scheduling and unlocked calls so one stalled receiver cannot block recovery controls (§4.1).

An absent daemon refuses; while forward admission is unready, the valid control surface reports ordinary lifetimes as unenforced/held and distinguishes standing allocations where expiry does not apply, elapsed-time holds and pending cleanup. Complete classification/confinement and accounting, rather than disappearance of every unknown, precede forward readiness (§7.1).

## 8. Operations, results and authorisation

### 8.1 Request `dispatch-op/1`

A discriminated union on `op`; every operation has a closed set of members, and members of other operations are refused (`request_invalid`). Rows marked as gated or partly unpublished specify semantics only; they cannot be enabled as an incomplete wire schema. Times are RFC 3339 UTC; durations are integers in seconds; lists have bounds.

Operator records for `team/1`, standing retirement/re-creation, maintenance stop authority and standing re-grants follow §3.2's phone or terminal custody/confirmation contract and MUST be refused when originating inside an agent session. They remain distinct from ordinary caller-request `auth`; their transport, canonical signature and refusal mappings would need publication (§16). `swarma-observer` is read-only: it can read dispatcher state (status, grants, accounts, bindings) without confirmation and cannot `cancel`, `retire`, `reconcile`, `drain`, renew authority or invoke bring-up. Grant/account/binding read representations beyond the existing status/list schema would need publication; no operation or member is added here.

E-rebind is the authorised renewal effect on an existing allocation (§3.4); its request/transport and broker binding-replacement grammar are unpublished. This does not invent a `dispatch-op/1` operation value. `network?` is checked against the machine-owned binding at `prepare`, never accepted as authority. Status reports credential horizons, unresolved effect/cleanup obligations and forward-admission closure separately from control availability; added representation details would need publication (§16).

For an ordinary allocation, omitted `max_runtime` uses §3.5's 4 h default; a supplied value is subject to the 12 h maximum and configured quotas. For a standing allocation, `max_runtime` MUST be absent; supplying it MUST be refused before launch, never used to install a deadline or silently ignored. The refusal-code mapping is unpublished (§16, question 8); no new code is asserted here. Allocation designation, not the requested duration, determines which policy applies.

### 8.2 Results

`dispatch-result/1`: `{ v: 1, request_id, ok: true, result: { … record … } }` or `{ v: 1, request_id, ok: false, error: { code, message, stage? } }`. A repeat of a completed request returns the stored result with the record's **current** state. The meaning of terminal outcomes is fixed: `exit` (the harness ended), `failed` (a stage failed and cleanup is confirmed), `cancelled`, `expired` (ordinary allocation lifetime or ordinary execution runtime; neither applies to standing allocations or their executions), `lost` (the holder vanished and the execution was stopped and confirmed absent).

### 8.3 Socket `dispatch/1`

Companion figure: [service daemon and gated SH2+ backend](../diagrams/v1-daemon.puml).

The daemon `swarma-dispatcher` runs as `swarma-dispatcher` and listens in `/opt/swarma/run/dispatcher/`. It uses the framing and connection rules of broker §4.1 and §13 with one declared difference: frames up to 128 KiB (§10). This is the service transport from slice 0, including the Curator CLI client. The broker rules include peer authentication, server-UID verification, protected endpoint/connection lifecycle and descriptor restrictions; descriptors are not a request transport. An absent daemon or authentication, permission, version or malformed-response failure refuses with no command fallback. Admission-unready is separate from control availability: after exclusive ownership, compatible schema, journal replay and valid authentication/indexes, the existing socket serves authorized recovery controls (§§7.1, 11). Forward readiness requires complete classification and safely bounded accounting; no alternate service or launch path is introduced. Later capabilities reuse this transport; queueing/events/long waits are omitted initially. After an ambiguous reply the client repeats the same request with the same `request_id` and signature.

| Operation class on the existing socket | During recovery / closed forward admission |
|---|---|
| own status/list/capacity, dispatcher reads by `swarma-observer` without confirmation, and receiver read-only observation through reconciliation | reachable after control prerequisites; expose unknown/held accounting honestly, no new launch grant |
| reconcile and already-authorised current-execution-bound `cancel`, `host_stop` or selected operator stop | reachable only with sound particular identity/authority; record intent promptly, unknown launch still waits for its receipt |
| provision/start/dispatch, `host_start` successors, E-rebind and other authority-creating work | require forward readiness, fresh authority/verdict and no record-local uncertainty; maintenance/restore/hold/time barriers still close them |

Receiver `effect.observe` remains the existing helper/broker API, not an invented dispatcher `observe` operation. Unsupported gated operations remain disabled.

### 8.4 Relation to the platform launch contract

The dispatcher implements a **local headless subset** of `dispatch(LaunchRequest)` (architecture §7.1, §5.1): it starts already composed plans; it records the opaque provenance (`board_ref`, `parent`) whole; it refuses interactive transport, native resume, seeded continuity and remote targets (`unsupported_combination`). Interactive executions under agent accounts arrive with the session host's platform phase (its backend gate, §12), not in this dispatcher (owner decision 2026-10-10); goals are optional. For now only the launching caller at start (through the launcher), or the board/orchestrator for board goals, authors a session goal (D-GOALS); an agent account has no goal capability on the session-host socket. This keeps authorship with the initiating caller while a separate agent namespace and its authority bounds await SH2+ design. The host must function without goals, a board, an orchestrator or their toolchain; board goals are an optional client of a generic goal interface. Choosing self-goals in a separate namespace versus caller/board-only authorship remains deferred (§16). A versioned LCH adapter, owned with the launch client, composes plans, compares pins and maps `LaunchRequest` onto these operations; until it exists, nothing claims full LCH conformance.

**Workplace backend (R-WORKPLACE; gated).** `workplace` is the project-side home/account allocation class of a remote worker. `swarma-rb-exec` runs under a service principal, never the workplace UID; policy, caps, durable effect claims, audit and certificate renewal control stay outside the worker's UID. A remote workplace requires enforced networking; it is admissible only after helper v1 on that host, with applied-state and loopback qualification (user manager §8). The helper owns the fixed SSH relay-stub account shape; dispatcher/host/broker sockets refuse workplace principals without configured roles. Host-local workplace jobs require a new qualified backend, not support inferred from the current remote-target refusal. Their wire names `swarma-rb/1` and `swarma-workplace-exec/1` stay unpublished (§§12, 14, 16).

## 9. Capacity

Figure M-DP2: [capacity ownership alongside allocation and execution claims](../diagrams/agent-claim-states.puml).

| Admission condition | Initial slice | Later queue capability |
|---|---|---|
| temporary capacity gate closed | refuse with `capacity:*` | queue with a durable handle; re-check authority and gates before starting |
| quota exceeded | refuse `quota_exceeded` | refuse `quota_exceeded`; never queue |
| authority invalid | refuse | refuse; never queue |

- **Claims.** A capacity claim is a durable record `{ claim_id, owner record, class, resources, expires_at }`, taken at `capacity`, transferred to the execution at `start`, released after confirmed end/absence, including cancel, expiry and reconciliation; unknown process evidence never releases it. Re-checks before the launch exclude the claim's own resources, so an admitted request never refuses itself.
- **Counters.** Allocations and executions are counted separately, per caller and in total.
- **Authority at admission.** Prepare and every start require a fresh `revocation.check` with the matching `prepare` or `start` context (§3.4); `revoked`/`unavailable` refuse before new effects, including broker restore fencing. Dequeue requires its own `dequeue` check, never a saved prepare verdict. Broker final checks remain independent and mandatory.
- **Gates** (architecture §5.1.4): `slots`; `disk` on every volume the run touches (agents root, dispatcher state, broker store); `cpu_idle` over a window; `hold` (the host-wide hold flag, read fail-closed: unreadable means held); `build_lock` and `syspolicyd` for job classes that build or create executables. The initial slice admits the job classes `agent-headless` and `agent-headless-build`; the second requires the build-lock and syspolicyd gates, which read the host's flags.
- **Queue (later capability).** Temporary gate closures queue a request with a handle; permanent refusals (quota, authority) never queue. The queue is bounded per caller and in total, fair across callers (round-robin by caller), durable, and re-checks principal, signature/window, quota, every gate and a fresh `revocation.check` with context `dequeue` at dequeue. `drain` either parks queued requests or rejects them, as the operator chooses.

Unresolved in-flight or restored work counts conservatively against quota/capacity; claim expiry is not absence. Forward admission of unrelated records requires §7.1 confinement and complete accounting. Unbounded accounting/shared integrity closes the node; bounded record-local uncertainty retains only its own claims. Recovery controls remain available under §8.3 prerequisites.

## 11. Installation and activation

Companion figure: [service activation and bounded maintenance](../diagrams/activation.puml).

- **Operator prerequisites (F-23 / R-OPERATOR).** Establish protected `swarma-operator` (no harness sessions), its broker operator/account-owner and user-manager `operator` roles, and mandatory read-only `swarma-observer` before operator acts are admitted. For the phone path, configure §3.2's pinned operator device key, SSH-over-tailnet key-only login and forced operator command with no shell. Install the password-authenticated terminal fallback (`timestamp_timeout=0`, no `NOPASSWD`). The terminal path works without a phone; no additional hardware or signature-algorithm change is mandated. Never restore operator signing authority into an account that hosts agent sessions. Key enrolment, rotation and phone loss remain open (§16), with terminal re-enrolment proposed.
- **Installation.** The installer creates `swarma-dispatcher` with the helper, places the binary in `/opt/swarma/libexec/`, writes only dispatcher-to-helper/launcher no-argument sudo rules, registers the service principal in helper policy and broker configuration, generates its key, and obtains the operator-issued constructible dispatcher grant (§3.4). It installs the daemon and protected Unix socket using the broker's service/connection rules. It requires an authenticated or operator-controlled time source (for example NTS) and the common time-confidence/monotonic-expiry policy (§§3.4, 5.4). With service-profile v1 enabled, it installs and verifies dispatcher deny-all egress under user manager §8, including DNS/resolver denial (§13). There is no caller-to-dispatcher sudo rule, detached-command bootstrap, external sweep timer or command-to-daemon conversion.
- **Readiness.** Start with admission closed, take exclusive state ownership, validate state reader/writer compatibility, replay the journal and reconcile effects, receipts and process evidence. Publish control availability once exclusive ownership, schema compatibility, replay and authentication/indexes are sound. Publish forward readiness after every record is classified and complete accounting confines unresolved effects to retained identities/claims (§7.1). Record-local unknown/contradictory evidence blocks that record; unbounded shared uncertainty blocks the node. Authorized observation/status/reconcile/stop remains reachable under §8.3. An absent service refuses without fallback.
- **Bounded maintenance attempt (R-MAINT).** Before a backend-mode change, mutable-state migration or binary swap: (1) close new admission; (2) durably inventory existing executions and selected stops; (3) require a signed selected-stop operator record under `swarma-operator` authority via §3.2's phone path (operator device key, biometric confirmation, exact content shown) or terminal fallback, with authentication and exact-content confirmation; refuse records originating inside agent sessions before any selected stop through the dispatcher and journaled helper `exec.stop`; (4) require confirmed process absence and reconciliation for all affected executions before changing mode/state/binary; the affected set is defined by the user manager §7 R-FATE table for the exact platform/unit configuration, never guessed from process parentage. Closing admission or draining queued requests does not stop a running execution. The maintenance deadline bounds this attempt, never a standing execution's lifetime. Unknown/refused stop, uncertain absence, incomplete reconciliation or deadline exhaustion defers maintenance with admission closed; no swap or migration is permitted. Progress and unresolved obligations remain durable for operator review and resumption using the same stop effects/receipts.
- **Retention and restart.** Maintenance keeps standing allocations and identities; it performs no automatic retirement, re-creation, live adoption or lifetime expiry. Persist intended restarts for operator review; a restart needs fresh authority, fresh `prepare`/`start` verdicts and an admitted plan/transport. Unsupported rows stay visibly stopped. Native resume is only available after its §12 gate; maintenance promises no seamless context continuation.
- **Cutover and rollback.** After confirmed absence/reconciliation, take exclusive state ownership, validate/migrate the schema and activate the selected binary/backend. Repeat recovery before publishing readiness. Rollback follows the same fenced absence and compatibility order, retains later durable records and never restores an old snapshot as a repair. A binary refuses unreadable or unsupported state; no live supervisor adoption is allowed. Maintenance authorization, deadline/progress and restart-review formats remain unpublished (§16); their wire fields/codes are not invented here.

### 11.1 State loss and restore (R-GEN)

State loss, unreadable state or a declared restore is distinct from ordinary crash replay. Keep node-wide forward admission fenced. Before restored bytes become visible, an operator establishes a restore mark/fence outside the restored failure domain, reusing the broker's fail-closed restore procedure (§15.4). A user-manager ledger restore closes every direct ledger consumer (dispatcher, broker, launcher, session host), not only `effect.observe`. The dispatcher records the highest ledger store epoch seen and refuses a lower one pending operator reconciliation; its floor is useful only if surviving outside the restored domain and cannot certify a whole-machine rollback. The fence/epoch/control-recovery formats would need joint publication (§16).

Restore or reconstruct private dispatcher state while ownership is exclusive. Treat pre-restore receiver coverage as `unavailable`, never `not_recorded`, until independently re-established against OS directory inventory, surviving root receipts/audit, broker tombstones, other component records and operator evidence. A restored snapshot cannot certify its own completeness. A generation seen `retiring`/`removed` in surviving evidence never returns `active`; an active ledger record with no OS account is contradictory, not creation to resume. Fresh generations reference user manager §4.1's random 128-bit allocator; old restored identities are not authenticated by randomness.

Reconcile both directions: existing dispatcher records, user-manager accounts with `created_by` equal to this dispatcher, its broker bindings and surviving receipts. Report unmatched objects as orphans, hold their identities and conservative quota/capacity obligations, and require an explicit operator-signed decision under §3.2's custody contract to retire or re-adopt their records. Names/UIDs alone authorise neither deletion nor adoption; no automatic orphan or live-supervisor adoption is allowed. Re-adoption does not create fresh mutation/launch authority or reactivate a retiring generation. Inventory and decision formats would need publication (§16).

If the ledger was also rolled back, recover post-snapshot objects from OS inventory, preserved receipts and operator evidence; lost evidence means coverage is unknown and bounded recovery is not promised. An undeclared internally consistent whole-machine rollback is not locally detectable. Reopen forward admission only after the external fence is reconciled, coverage and non-resurrection are established, and §7.1 classification/accounting holds. Safe recovery controls may be served under §8.3 while forward admission stays fenced.

## 12. Session-host backend (later; activation gate)

Companion figure: [backend process identities, host admission and recovery](../diagrams/v1-daemon.puml).

Before the SH2+ session-host module may hold executions through its agent-side runner (not the service UID):

- **Owner admission (R-SESSION).** The owner's admitted `start` explicitly carries session lifecycle authorisation when successors are allowed (§§3.4, 4.2). Same allocation/generation, stored plan verbatim and owner's grant window bound it; ordinary allocation lifetime and cumulative/anchored restart budget also bound it. A one-start request admits only that start. The original caller ancestry stays the broker dependency; the host never obtains a caller chain.
- **Session permit and physical start (R-START / R-SESSION).** The durable **host admission permit** is session-scoped for one `logical_session_id`. Only the configured session-host principal invokes `host_start`, carrying `(logical_session_id, execution_id, controller_epoch, op_id)` and referring to that permit. Every physical start has its own claim, epoch/fence, distinct E-launch and root-receipt interlock. The host first persists intent with delivery closed. Dispatcher alone calls `swarma-user-launcher`; the host has no launcher sudo authority, helper host role or delegated root start authority.
- **Host stop.** Only the configured session-host principal may invoke `host_stop` for an execution under its permit. It uses the journaled E-stop path, user-manager `exec.stop` single account-wide scope and confirmed absence (§§4.5, 5.3, 6); it is durably host-requested, distinct from owner `cancel`, and confers no start authority. Unknown launch/stop evidence retains claims and waits for the same effect/receipt; old execution receipts cannot stop successors.
- **Cancellation and withdrawal.** Owner `cancel` or `retire`, revocation/expiry of the owner's chain, an operator-signed standing-retirement record or R-MAINT durably withdraws successor authority, serialised with admission under the state lock; no autonomous repeat follows cancellation. Unknown permit state closes successor starts. Cancellation before call issue prevents the call; after issue, resolve the same effect/root receipt and stop if required, never launch twice. Host failure keeps claims and delivery closed until reconciliation. Publication would need the authenticated withdrawal call/encoding; no new operation value is invented here.
- **Fences without cross-service locks (R-LOCK).** The host owns durable per-session fences and validates its current epoch locally; it holds no fence/state lock across `host_start` or `host_stop`. Dispatcher validates the submitted four values at each effect under its local lock, marks the record in flight, then releases it for receiver I/O. A mid-call host fence change requests withdrawal through a second call. The post-call handler rechecks epochs/fences; stale results cannot open delivery (§4.1). Atomicity is per effect at the receiver, never a cross-service lock. Controller-only re-adoption keeps `execution_id` and needs no permit action; execution replacement uses a new ID under the successor rules below. This permits no live supervisor adoption in dispatcher maintenance.
- **Registration before delivery.** The approved agent-side runner opens a fresh authenticated host channel. Current-controller-epoch registration and readiness precede delivery; a closed fence or stale epoch refuses delivery. The runner checks the exclusive native-session lock (R-HOLD-OLD/R2).
- **Ownership and fate (R-FATE).** Dispatcher owns admission, privileged physical starts, records, stop and cleanup; host service owns metadata, logs, receipts, fences and input admission; agent-UID `swarma-session-runner` owns PTY/app-server transport and credential renewal. Account generation, execution claim epoch, daemon-instance epoch and controller epoch are distinct. User manager §7's fate table defines exact platform/unit survival and maintenance affected sets; no survival is inferred from `setsid` or UID changes. Host/runner is a later qualified consumer; host service embeds no broker client. Every handoff is published before activation.
- **Publication gate (I4).** The session lifecycle authorisation member and ordinary restart-budget format, session-scoped permit/reference, `host_start`/`host_stop` authentication, host-requested record representation, withdrawal durability, per-use replay/claim/crash ordering, root/host receipts and ownership handoffs would need joint publication and qualification (§16). No tickets exist. Naming the semantics does not publish unspecified wire members, values or refusal codes; the backend stays disabled.
- **Native resume (D-RESUME; later backend only).** On the same machine, a non-breaking harness version change is allowed by semver: same major, and for 0.x the same minor, without an extra qualification row. A different major or 0.x minor refuses. Retain the same runtime family, managed home, profile pin, transcript integrity, exclusive native-session lock, ready authentication and current grants. A harness resume failure is reported as `resume-failed` for the caller to decide; no automatic fallback or portable seed is part of resume. A per-harness note records vendors known not to follow semver. This does not enable resume in the current local headless subset (§8.4).

| Successor `host_start` admission | Required behavior |
|---|---|
| owner lifecycle consent absent / replay of one-start request | no successor; fresh checks cannot substitute for consent |
| repeated `(logical_session_id, op_id)`, including after host/dispatcher crash | return the same recorded successor and effects, never create a second; changed intent conflicts under existing replay rules |
| previous execution claim not confirmed absent | refuse `agent_busy`; unknown is not absence |
| plan, profile pin or posture diverges | new owner admission required; host supplies no replacement plan bytes |
| owner principal retired/inactive, chain expired/revoked, or fresh `revocation.check(start)` unavailable | no physical start; original ancestry remains mandatory |
| ordinary lifetime or cumulative/anchored restart budget exhausted | no successor; restarting never extends lifetime or resets runtime windows |
| valid consent, current owner/chain/window, fresh start verdict, confirmed absence, unchanged plan and current fence | new execution claim and distinct effects under the session permit; standing runtime stays unlimited |
| controller-only re-adoption | same execution ID, no physical start or permit action; host delivery fence still applies |

The permit does not choose the reboot requester. The host or project registry remains an open publication choice (§16); whichever is configured acts only within the owner's session lifecycle authorisation.

**Workplace gate (R-WORKPLACE).** A workplace is a separate project-side allocation/backend (§8.4), not an agent-account session backend enabled by SH2+. `swarma-rb-exec` is service-owned; workplace jobs use the dispatcher-owned launcher, root receipt and `exec.stop` path under the workplace UID. Before enabling it, publish one-job-per-execution versus a standing workplace-runner shape, concurrency/blast radius and current-execution fencing. In the runner shape, per-job process-group cancel is best effort; unconfirmed descendants require account-wide runner stop, retained unknown job claims and no effect replay, then freshly admitted runner restart. Publish service-principal policy/effect/audit custody, fixed SSH relay entry, user-CA custody, enforced-network/applied-state and loopback evidence. OS-user write scope is the UID's writable set and network mode is the per-UID firewall; stronger scope claims need a qualified backend. `swarma-rb/1` and `swarma-workplace-exec/1` remain unpublished and workplaces stay disabled until these gates hold.

## 13. Security

- Unprivileged; its powers are its helper role (its own agents), its broker role (their bindings), the launcher rule, the stop operation, and its key, which signs leaves only inside its own grant.
- Callers are authenticated by the kernel and by request signatures; plans are opaque; the dispatcher never reads Curator fragments or credentials.
- An agent that compromises its own account cannot reach the dispatcher's state, key or sudo rules; it can call the dispatcher only as a caller with its own grant.
- **Service egress (R-SVC-EGRESS).** Dispatcher has none: deny-all, including loopback TCP, under user manager §8's v1 service-profile rows; Unix-socket IPC remains usable. No local DNS is needed. Resolver denial (including Mach/XPC paths on macOS and resolver sockets on Linux) must be separately qualified; per-UID packet rules alone are not DNS evidence. Verify the row and parent anchor at every service start and on the published helper-owned schedule. A missing row/enforcement lapse raises an incident and drops forward readiness; safe recovery controls and process response follow §§7.1, 8.3 and R-FATE. Periodic checks have a detection window and do not promise continuous enforcement. This v1 capability does not claim slice-0 kernel containment or disable the software-root slice; formats, schedule/owner and per-OS evidence would need publication (§16).
- Logs: the executor's output is stored with size bounds in the dispatcher state; the qualification scans these logs, the executor and broker artifacts for credential material; the trusted boundary is the executor and the harness release it qualified (broker §12.2).
- The audit log records each request, decision, effect and cleanup as typed metadata.

## 15. Qualification

On hosted CI runners only, through the deployed clients (`curator agent-user` and `curator-dispatch`), the slice-0 `dispatch/1` socket and exactly the deployed dispatcher-to-helper/launcher sudoers rules. These are qualification requirements, not locally executed evidence:

- `dispatch`, and `provision` then `start` twice in sequence, with the broker's slice 0 and one Claude launch each;
- authority: a copied chain from another caller, a missing or wrong signature, an unregistered key, an unconstructible request, a revoked caller grant (the agent's next lease refused), a recycled UID;
- crashes on both sides of every acknowledgement (input, effect intent, effect result, claim, supervisor registration, start receipt, termination receipt), each followed by reconciliation;
- cancel in every state; ordinary execution `max_runtime`; ordinary allocation expiry with and without the sweep; a lost supervisor with escaped descendants;
- standing allocations: no expiry/lifetime quota; sweep never expires them; caller `agent.spawn` cannot retire, re-create or bring up the team; absent or invalid operator signatures authorise no team effect; operator-signed retirement/re-creation only;

Admit phone signatures only after exact content display and biometric confirmation against the pinned key; admit password-authenticated terminal fallback with content confirmation. Refuse agent-session origin even with an otherwise valid signature, wrong/unpinned signer, missing authentication/confirmation, changed canonical content, cross-act signature reuse, phone shell/password-login access and terminal `NOPASSWD`/cached-ticket reuse. Automatic renewal cannot manufacture operator consent; publication/qualification remains outstanding, not test evidence;

## 16. Open questions

1. **Retirement policy (F-1; CLOSED — owner-decided 2026-10-12):** ordinary retirement deletes the home after quiesce and declared-key cleanup. Dispatcher cleanup admits only `delete`; retention is a separate explicit operator operation with no confidentiality guarantee (§5.4). The user manager would need to publish its retention operation and closed-schema service-metadata export; no general secret classifier or archive-by-default alternative remains.
2. **Helper v2 signed requests (contract W3; OWNER DECISION NEEDED, user-manager/contract owners):** publish a component-specific format or a versioned shared adapter. D-WIRE-NAMES supplies the naming rule but not the signature domain/version and canonical bytes. The helper's initial contracts use authenticated dispatcher sudo caller and role policy, not an invented signed-grant verifier.
3. **Host admission permit (contract I4 / R-START):** launch tickets and the old launcher-redemption resolution are removed by the owner decision of 2026-10-12. R-SESSION refines R-START: joint publication would need the owner's session lifecycle authorisation member, cumulative/anchored ordinary restart budget, durable session-scoped permit for `logical_session_id`, per-physical-start `(execution_id, controller_epoch, op_id)` claims and replay relation, `host_start`/`host_stop` authentication/member formats, host-requested stop representation, authenticated withdrawal call, admission/withdrawal/cancel/crash ordering, receipts, registration/readiness and handoffs. The reboot requester (host or project registry) would need to be selected; neither gains authority beyond owner consent. Exact refusal mappings would need publication; no new code is invented. The SH2+ backend stays disabled (§12).
4. **Agent self-goals (contract G2; deferred SH2+ owner decision):** (a) a separate agent namespace with its own bounds, or (b) retain caller/board-only authorship. Neither requires goals or a board for host operation (§8.4).
5. **Log-storage handoff:** retain dispatcher execution logs or transfer them to the host's durable log store when the backend activates; the ownership handoff must be specified first (§12).
6. **Standing-session execution runtime (R3; CLOSED — owner-decided 2026-10-12):** the owner decided that the orchestrator and standing team members (other orchestrators and standing agents) have no predefined allocation expiry or maximum execution runtime; only an explicit stop or the operator stops them. This supersedes the R3 proposal and applies to executions of standing allocations in all backends, not only SH2+. They have no `max_runtime` quota or runtime deadline, and the sweep never stops them for runtime (§§3.5, 4.4, 5.3, 7.2). Own exit and incident hard stop still end an execution through confirmed absence. The 4 h default and 12 h maximum apply to every other execution.
7. **Orchestrator child-plan access:** which profiles and environments may an orchestrator read and use for its children from its agent account, and how does its narrowed grant constrain that access? Caller-side composition with the orchestrator's own home configuration is decided (§5.2); the read/access policy is unspecified.
8. **Standing/team wire publication (F-23 / R-OPERATOR):** custody is decided in §3.2: `swarma-operator` via the phone operator device key or terminal fallback, exact-content confirmation and agent-session refusal. Publication would need the standing designation in `agent/1`, the operator-signed retirement/re-creation record, and the remaining envelope, signature grammar, transport, role matching and change semantics for the specified-but-unpublished `swarma-dispatcher team/1` (§§4.3, 5.4–5.5). Only per-role `label`, `profile`, `harness`, `accounts` and `capabilities` are specified here; no additional fields or values are asserted. Publish the refusal-code mapping for `start` with `max_runtime` on a standing allocation (§8.1); if an existing code cannot represent this refusal, it would need a published refusal code. No code is invented here; the runtime policy itself is decided in question 6.

9. **Orchestrator bootstrap (R-DELEG):** would need the generation-bound enrollment intent, pre-key proof-of-possession domain/canonical bytes, authenticated freshness/replay window and identity, rotation/operator-recovery authorization, requester-signed delegation installation operation and durable activation/acknowledgement ordering (§§3.3–3.4, 5.2, 8.1). Depth/chain preflight and requester ancestry are fixed; wire members and refusal mappings remain unpublished. Recursive provisioning stays refused until publication and qualification.
10. **Revocation verdict (R-VERDICT):** would need exact `broker/1 revocation.check` chain/context and sequence encoding, configured-dispatcher authentication, bounded response/freshness handling and dispatcher refusal-code mapping for `revoked`/`unavailable`, including restore fencing. Contexts and verdict names are fixed (§3.4); final broker checks stay mandatory.
11. **Receiver observations (R-OBS):** would need exact `effect.observe` encoding, canonical argument digest format, original-caller/operator authentication and journal serialization, helper and broker retention floors, matching unbind removal/tombstone retention and lost-evidence behavior. Six states and their mapping are fixed (§§4.5–4.6, 7); expired/unavailable evidence never proves absence.
12. **Maintenance authorization (R-MAINT / R-OPERATOR):** `swarma-operator` signs selected-stop authority through §3.2's phone or terminal path, with exact-content confirmation and agent-session refusal. Publication would need its signature/record and origin/confirmation evidence, bounded attempt deadline/progress persistence and restart-review formats, interruption/resumption ordering and reader/writer compatibility qualification (§§8.1, 11). No maintenance deadline limits standing runtime.
13. **Service capability publication / R-FD3:** later queue/events/long-wait negotiation and unsupported-capability refusal mappings would need publication on the same `dispatch/1` transport. User manager §7 would need the per-platform fully staged, bounded immutable read-only FD3 mechanism (or qualified pipe capacity/feeder/deadline/cleanup ordering) and lifecycle qualification before launch activation; this dispatcher references that single contract (§5.3).

14. **Renewal (R-REBIND / R-OPERATOR):** standing re-grants require §3.2's signed `swarma-operator` phone or terminal act with exact-content confirmation and agent-session refusal. Automatic bounded non-widening standing re-grants would need an existing published delegation; none is published here. Publication would need the authorised renewal request/transport, canonical arguments and current-chain installation (including requester-signed descendant selection), broker binding-replacement/old-tombstone observation grammar, horizon status encoding and renew-ahead policy. A fenced fresh-lease handoff or explicit park/restart must be published/qualified before claiming running continuation (§§3.4, 4.3, 7.2). E-rebind is fixed; no new `dispatch-op/1` value is invented.
15. **Restore (R-GEN):** would need external restore-mark/fence placement and consumer closure/reopening, ledger store-epoch/floor encoding, independent coverage evidence, reverse inventory APIs, orphan reporting/reservations and operator-signed record retirement/re-adoption formats (§11.1). Random 128-bit generations and no resurrection are fixed; whole-machine rollback/lost-evidence detection is not promised.
16. **Time (R-TIME):** would need one shared time-confidence policy, tolerance/sync/operator evidence, durable watermark/reset and boot-inclusive elapsed accumulation formats (§§3.4, 5.4, 7.2, 11). Reset must preserve genuinely expired authority; expiry destruction needs both wall expiry and monotonic lifetime.
17. **Lock and fate (R-LOCK / R-FATE):** would need per-record durable in-flight/version/daemon-instance encodings, call-issue/cancel/late-result qualification and bounded worker/deadline policy; user manager §7 owns per-platform unit configurations and fate-table evidence (§§4.1, 6, 12). No containment unit or resource ceiling is invented; singleton/process ownership is separate from state locks.
18. **Outcome and retirement (R-OUTCOME, F-12/F-25):** receiver-owned per-operation tables, unchanged-argument continuation/retention and direct-operator broker-cleanup obligation reporting would need publication (§§4.5–4.6, 5.4, 7). The helper owns cleanup quanta/dependency bounds and fair forward progress; no new cleanup timer or success state is invented.
19. **Workplace (R-WORKPLACE):** would need the `workplace` allocation/request encoding, service-principal/control/user-CA custody, fixed SSH relay entry, job-versus-runner/concurrency/blast-radius policy, enforced helper-v1 networking/loopback evidence and qualified launch/stop backend (§§8.4, 12, 14). `swarma-rb/1` and `swarma-workplace-exec/1` stay unpublished; no remote support is inferred.
20. **Service egress (R-SVC-EGRESS):** would need helper-v1 service-profile operation/role extension, deny-all dispatcher row and DNS/resolver evidence, scheduled verification owner/interval and incident/readiness response (§13). Periodic detection is bounded by its window; software-root slice 0 stays available.
21. **Network binding (R-NETBIND):** would need the user-manager §8 machine-owned binding location/schema, Curator profile lock identity and ref/digest input-pin encoding, canonical relation to served allowlist digest, listener/service-generation lifetime attestation and narrowing re-apply trigger plus proxy-side session drop/recheck. The distinct linked record/effect for an authorised narrowed-policy pin, its relation to the immutable original `input/1`, and its authorisation, canonical arguments and retry/recovery encoding would need publication; each effect retains its own pin. Policy/catalog drift against that pin refuses; no network grant dimension is added (§§3.4, 5.1, 8.1).
22. **Cross-account workspace (F-16):** standalone/private writable Git administration is owner-decided. Workspace-capable activation would need approved source/result transfer owner/path/authorization and any immutable object-store provenance/access/retention; exact admitted base and fresh configuration/hooks remain mandatory (§§5.2, 14). Same-account worktrees and today's board workflow stay.
23. **Recovery/control publication (F-15):** would need status representation for forward-readiness versus control availability, complete accounting/confinement evidence and unresolved effect/cleanup reporting. The operation-availability matrix is fixed (§§7.1, 8.3, 11); unknown never becomes absent and no alternate launch path is added.

24. **Operator custody publication (F-23 / R-OPERATOR):** the account names, no-harness boundary, phone-first signing, terminal fallback, exact-content confirmation, agent-session refusal and mandatory confirmation-free observer reads are owner-decided (§§3.2, 5.4–5.5, 8.1, 11). Publication would need the operator command binary name/wire format, operator-record signature domain/canonical bytes, per-act replay binding, pinned-key verification and origin/confirmation evidence, terminal signing contract, observer read representations/access policy and refusal-code mappings. Key enrolment, rotation and loss of the phone would need a recovery procedure; terminal re-enrolment under the fallback path is the proposal. Loss of operator authority follows the broker root-replacement procedure, never key restoration into a session account. No new fields, codes, values or algorithm changes are asserted.

The executor and first consumer are decided by D-EXECUTOR, managed PATH by D-PATH, wire names by D-WIRE-NAMES, and resume compatibility by D-RESUME; their older open questions are superseded. Default quotas and ordinary allocation lifetimes are already decided and configurable (§3.5); the owner decision of 2026-10-12 closes R3: standing allocations have no expiry/lifetime quota and their executions have no runtime quota/deadline. Every other execution retains the 4 h default and 12 h maximum. Interactive execution remains gated on the session host. Donor provisioning belongs to a separately specified small privileged component, not a user-manager extension (D-DONOR-PROVISIONING); variant B stays disabled until that component is specified, and remote targets remain outside this subset.
