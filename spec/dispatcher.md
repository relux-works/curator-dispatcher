## 1. Purpose

The dispatcher is where a launch becomes an execution. It takes from today's `task-board spawn` the part that starts executions and keeps their records, and makes it a module that works with or without a board:

1. it accepts a request from a person, an orchestrator, the board or a tool, authenticates the caller by its OS account and its request signature, and checks the caller's grant;
2. it checks and reserves this machine's capacity;
3. it provisions an account through swarma-user-manager; a trusted agent gets a credential binding with a narrowed leaf and caller dependency, while an untrusted allocation never gets a subscription binding or lease (§3.6);
4. it starts the agent's executor under that account through the helper's launcher, tracks the execution, and stops it through the helper when asked;
5. it cleans up per policy, and after any crash reconciles its records with the helper, the broker and the process evidence, including reverse inventory after state loss, before admitting new work under the confinement rules of §7.1.

Without a dispatcher, Curator can still launch directly, without accounting; with one, everybody launches through it. The board and its toolchain are optional clients, never dependencies of this module.

### 1.1 Non-goals

- It does not choose roles, models or efforts, and does not compose executor plans; it pins their bytes and digest. This does not permit opaque signing-plan content: purpose-6 adapters must independently validate complete protected typed plans (§3.3).
- It does not hold credentials and does not run as root.
- With a session host present, it does not hold processes (§12).
- It does not decide when board work is accepted; the board's own completion barrier stays with the board (§14).

### 1.2 Names

| Name | Meaning |
|---|---|
| dispatcher | this component, under its service account `swarma-dispatcher` (names follow the platform root `/opt/swarma`) |
| caller | the principal that sends a request: a person's account, an orchestrator agent, the board's runner, the session host |
| agent allocation | one provisioned agent account generation and what the dispatcher keeps about it (`agent/1`) |
| execution | one start of one plan under one allocation (`run/1`) |
| host launcher | `swarma-user-launcher`, the privileged transition into an agent account (helper repository) |

Long-lived sessions use `swarma-session-runner` under the agent account instead (SH2+, §12). |
| supervisor | the dispatcher-owned process that holds one execution (inside the daemon) |

### 2.1 Full protected-launch target and dependency gates

The minimal full protected-launch target is one non-federated trusted worker under its own station account through the dispatcher. It describes the full contract and its dependency gates, not the selected immediate milestone or an available launch path. Registry federation/publication is not required for this target; purpose-2 registrar enrollment cannot enroll purpose 6. The selected association direction is protected association at the dispatcher (§3.3), with no invented registry call or unsigned-row substitute.

A proposed reduced launch/lease milestone would use the standalone v0 credential lease without claiming full binding or narrowed credential-grant acceptance. It is a separately gated contract: the limited caller launch-authority/currentness policy is unresolved. Launch remains unavailable without an explicit owner-approved limited policy, jointly published and qualified, or real broker slice-0 grant/revocation integration. A credential UID allowlist or authenticated signature alone supplies neither launch authority nor freshness. The separate [DRAFT M0 candidate](m0-launch.md) proposes one bounded existing-worker policy/request variant for joint review; it is unaccepted and inactive. All full grant, freshness and binding requirements below remain intact (§16 question 33).

The [full helper design][helper-design] and [full broker design][broker-design] define the target boundaries. Their narrower releases do not supply those joins: [station v0][station-v0] has no launcher, general list, `effect.observe` or `exec.stop`; `active` means locally provisioned, not launchable. Its retirement is operator-only with an explicit, authenticated, exact-content-confirmed per-act export waiver; dispatcher retirement with export confirmation is later work. [Standalone broker v0][broker-standalone] uses a static operator UID allowlist and excludes signed grants, delegation, revocation, bindings and dispatcher integration. It cannot substitute for dispatcher caller authority. These source pins describe contracts, not deployed or qualified capabilities.

## 3. Identities and authority

### 3.1 The dispatcher's account

The dispatcher runs as the unprivileged service account `swarma-dispatcher`, created by the helper for the installer. Only this account is a **dispatcher** in the helper policy and in the broker, so the root transitions and bindings are reachable only through it. The dispatcher is a trusted principal for its scope: a compromised dispatcher can sign leaves within its own grant and administer the agents it created, but cannot exceed the broker-verified root bounds or obtain a general root shell from the helper's closed operations.

### 3.2 Callers

- The caller is the kernel-reported peer UID on `dispatch/1`, with the broker's connection rules (§4.1): protected socket directory and endpoint, client verification of the server UID, bounded authenticated connections and descriptor-inheritance/passing restrictions. Caller-to-service sudo authority is absent; dispatcher-to-root helper and launcher authority remains (§11).
- Principals follow broker §4.2: managed callers by `(uid, generation)` with the helper ledger showing the generation `active` (re-checked for every operation, every queued start and every reconciliation); unmanaged callers pinned by UID and directory identity. An unreadable or invalid ledger refuses; a recycled UID never inherits old allocations or executions.

**Operator custody (R-OPERATOR; owner-decided 2026-10-12).** The dedicated account `swarma-operator` MUST NOT host a harness session. It, rather than the person's interactive account, is the configured broker operator and account owner, the user manager's `operator` UID, and the holder of operator signing authority, including the broker v0 root and signed operator records. Operator binaries and configuration are protected from agent writes. Interactive agent sessions have no operator authority. The mandatory read-only account `swarma-observer` admits dispatcher state reads without confirmation (§8.1), including status, grants, accounts and bindings as represented by the dispatcher; it confers no mutation or direct helper/broker operator authority. Read representations not already specified would need publication (§16).

The main operator path uses an **operator device key**, hardware-backed and presence-gated, in the phone's Secure Enclave or StrongBox. The key MUST NOT leave the phone and is usable only after biometric confirmation. The phone app connects by SSH over the tailnet into `swarma-operator`, with login by that key only and no shell: a forced narrow **operator command** accepts operator acts only. Before signing each act, the app shows its exact content (who, which actions, until when); the machine verifies the signature against the pinned phone key. Each operator act is a signed operator record bound to that one act's canonical content; its signature cannot be reused for another act. The operator device key is an admitted signer for `swarma-dispatcher team/1` and standing-retirement records. The operator command binary name/wire format, signature domain and canonical bytes remain unpublished (§16); this does not change the published caller-request or broker signature algorithms or formats.

The terminal fallback uses password-authenticated `sudo` into `swarma-operator`, with no `NOPASSWD` and no cached ticket (`timestamp_timeout=0`), and produces records under that account's signing authority. It works without a phone. Widening acts require authentication plus confirmation of the exact act content: grant issue, subscription enrolment, `team/1`, standing retirement or re-creation, explicit home retention, maintenance stop authority, standing re-grants, export-obligation waiver, per-host soft-row acceptance, explicit emergency-stop recovery and trusted-circle admission. The operator CLI MUST refuse every operator act from inside an agent session; dispatcher admission MUST refuse every operator record originating there, even with an otherwise valid signature. This origin refusal covers widening and narrowing acts alike, including revocation, disabling an account and the node-wide emergency stop. Narrowing acts (revocation or disabling an account) require authentication only; phone revocation takes a single biometric confirmation. R-ALLSTOP is the node-wide narrowing act with authentication and one confirmation on the phone path, or the terminal fallback (§6); it is never automatic. Export-obligation waiver, per-host soft-row acceptance and explicit emergency-stop recovery are widening acts: each requires authentication plus exact-content confirmation. A refused export is retained by default: bounded repair needs current work authority (§5.2), and exhaustion or unavailable authority leaves a per-act operator waiver as the data-loss disposition. The operator-presence cost remains; standing discard of refused exports is an optional owner policy, unchosen and off. Their formats remain unpublished. Reads use `swarma-observer` without confirmation. `NOPASSWD` is reserved for the dispatcher service account's helper and launcher rules (§11). Already-authorised bounded service effects retain their existing authority; they cannot mint a new operator record or confirmation. Origin/confirmation evidence, terminal signing format and key enrolment/rotation/loss recovery would need publication (§16).

### 3.3 Caller keys and request signatures

- **Custody and protected association.** The newer [Keymaker station-caller proposal][station-caller] (§§1–5, 8) supersedes the historical home-generated key and available operator-enrolled bootstrap paths. `station-caller = 6` is approved, but not allocated or active. Ed25519 private keys, seeds and chain codes remain in Keymaker custody, with no readable private key, export, interim Git key, SSHSIG or arbitrary/opaque-byte signing fallback. Protected association at the dispatcher is the selected direction; it must bind the caller key to the authenticated principal's current generation and execution/profile/receiver scope. Stable public bytes or account recreation never restore an old association. The protected operator service root retains its separate authority and recovery prerequisites; it is not a station caller key and is never restored into a station.
- **Closed bootstrap.** Purpose allocation, complete protected typed-plan schemas/catalog/provenance and bounds, both versioned request/delegation adapters, association/currentness, proof/replay/rotation and durable authority installation remain unpublished or unqualified. Both operator-enrolled station bootstrap and recursive delegation MUST remain disabled until their dependencies are jointly published, implemented, independently qualified for the exact native tuple and explicitly activated by the operator. Operator-installed public associations are a possible first publication step, not an exception. `register_key` remains specified but unavailable under these gates; registration alone never grants spawn authority (§5.2). No purpose-2 registrar proof, registry row, Git key or opaque body substitutes for a missing join.
- Except for the narrow pre-key `register_key` exception below, every mutating `dispatch-op/1` request carries `auth: { key, sig }`: an Ed25519 signature by a caller key over the exact preimage `ASCII("swarma-dispatcher request/1") || 0x0a || CCJ-1(R)`, where R is the request without `auth`, with no terminating LF. The qualified adapter constructs R from the complete protected typed plan and inserts `auth` afterward without changing R; neither a digest in place of R nor a native-frame/SSHSIG wrapper is signed. The key must be associated with the authenticated principal (`caller_key_not_associated`), and the leaf of the caller's grant chain must have that key as its subject (`grant_subject_mismatch`).
- **Wire naming (D-WIRE-NAMES).** Repository-qualified signing domains use `swarma-<component> <object>/<n>`; wire kind discriminators retain their individually registered owner spelling, transport/schema labels retain their owner-published short forms, and provisional design labels confer no admission. The signed request domain above is exactly `swarma-dispatcher request/1`; the request-signature newline does not apply to the effect hash (§4.5). Broker signed domains are `swarma-credential-broker grant/1` and `swarma-credential-broker revocation/1`. Nothing has shipped, so these clean names require no migration or legacy-domain acceptance. This decision supersedes the contract table's W2 retention baseline; it does not publish the helper v2 signature grammar (§16). The existing dispatcher transport/schema labels `dispatch-op/1`, `dispatch-result/1`, `dispatch/1`, `input/1`, `agent/1` and `run/1` remain distinct from the signed domains; `swarma-dispatcher team/1` and `swarma-dispatcher workspace-result/1` are repository-qualified object-kind discriminators, not request-signature domains. The shared [naming index](https://github.com/relux-works/wiki/blob/main/naming.md) owns the typed rule and wire/format register: `R-` is reserved for shared rules, each resolving to one authoritative owner section. This module cites that index rather than defining another rule register; historical audit rows are not rules. Its docs gate must check unique rule resolution, existing owner sections, typed format references and the absence of operative pending launch-ticket references. Register rows and mechanical-check publication remain cross-module prerequisites (§16), not checks claimed here.
- A valid chain presented without the matching principal and signature is refused; a copied chain is useless to another caller.
- **Pre-key registration exception (R-DELEG).** Only the authenticated allocation's own active `(uid, generation)`, already selected for orchestrator enrollment by valid requester/operator authority, may register its first caller key. This exception permits key registration with proof of possession of that key, never `provision`, `start` or spawn authority. It does not use a nonexistent previously registered key. The dispatcher durably binds the enrollment intent, generation, key and registration replay evidence before acknowledgement. An exact replay returns the same registration; a changed key or enrollment intent refuses, a reused UID cannot replay a former generation's registration, and unavailable replay evidence keeps registration closed. The proof-of-possession domain, canonical bytes, freshness window and replay identity are unpublished (§16); the exception is disabled until these are published and qualified.
- **Rotation.** A new key requires proof of possession and authorization by the currently enrolled key within its current authority, or explicit operator recovery if that key is unavailable. Rotation is journaled and serialized with activation: the old key loses its association, stale registration replays cannot restore it, and a replacement delegation to the new subject must be verified before caller authority is active. Registration never silently rotates a key or transfers authority. The rotation signature/replay format and operator recovery authorization would need publication (§16).

### 3.4 Grants and their constructible shapes

These are the full broker-design requirements, not capabilities of the standalone v0 extraction (§2.1). The credential-binding shapes below apply to trusted agents. Untrusted/workplace admissions retain caller authentication and applicable authority checks, but never acquire a subscription leaf, binding or lease; their backend/wire publication remains gated (§§3.6, 12).

- **Action vocabulary:** `agent.spawn` (may ask the dispatcher to provision and start agents within the grant's accounts, harnesses and profiles) and `credential.lease` (may lease those accounts). Unknown actions refuse (`grant_unsupported`).
- **Caller chain:** the caller's leaf grant names the caller key, allows `agent.spawn` and `credential.lease`, and has remaining depth ≥ 1. It chains to a configured root under the broker's verifier (broker §6.2), at most 4 envelopes.
- **Dispatcher chain:** the dispatcher's own grant names the dispatcher key, allows `credential.lease`, has depth ≥ 1, and is at most 3 envelopes long, so an agent leaf can be appended within the 4-envelope bound. The installer refuses to configure a dispatcher chain outside this shape.
- **Agent leaf:** signed by the dispatcher key under its own chain; subject `agent:<generation>`, depth 0, action `credential.lease` only; accounts, harnesses, profiles and window are the intersection of the request, the caller's grant and the dispatcher's grant. A request whose intersection is empty or whose leaf could not be constructed is refused before any account is created (`grant_unconstructible`).
- **Caller dependency:** the binding carries the caller's chain and the exact intersection (broker §7, revision 0.3). The broker verifies both chains, separately, at bind, lease and every renewal, against the current revocation state: revoking the caller's grant or key stops new leases and renewals for every agent provisioned under it immediately. Tokens already delivered remain valid until they expire or are revoked at the vendor.
- **Orchestrator delegation preflight (R-DELEG).** For requester C to delegate spawn authority to O, C's chain must leave depth for O's `agent.spawn` and `credential.lease` leaf: C's leaf depth ≥ 2, O's depth strictly smaller and ≥ 1, and C's chain plus O's envelope ≤ 4. Each edge uses the parent subject as issuer. The dispatcher chain remains lease-only and never substitutes for C's caller ancestry. Insufficient depth or chain length refuses before account creation.
- **Revocation verdict (R-VERDICT).** At prepare, dequeue (when enabled) and every start, the configured dispatcher calls broker `broker/1` method `revocation.check` with the exact caller and dispatcher chains being checked and context `prepare`, `dequeue` or `start`. The broker answers `not_revoked`, `revoked` or `unavailable`, together with its revocation sequence at the check. Only `not_revoked` passes this check; `revoked` and `unavailable` refuse before new effects. Fenced broker restore answers `unavailable`. The verdict is point-in-time evidence, never a grant or a future-start permit; no cached verdict substitutes for a new admission check. Exact encoding and refusal-code mappings would need publication (§16).
- **Delayed and recovered forward work** (a queued request, a start after `provision`, or worker repair) re-checks the caller principal, request signature and validity window, caller chain and a fresh `revocation.check` verdict before acting. The broker's final bind, lease and renewal checks remain mandatory; an earlier verdict cannot prevent later revocation.

**Workspace cleanup consent (R-TRANSFER).** Original workspace admission MUST explicitly authorize bounded continuation of its durable export obligation after ordinary caller/request-window or allocation expiry. Consent binds the exact allocation generation and round, approved exporter digest, immutable B/manifest/write scope, pinned caps and cleanup bounds (§§4.2, 5.2). It authorizes only collection by that exporter: no harness, subscription lease, network, new task, ordinary successor or worker repair. Each cleanup start verifies this retained consent, sound current generation/identity, pinned executor/profile and fresh revocation/security-hold evidence through the existing admission boundary; ordinary expiry alone need not renew work authority. The cleanup check's exact encoding and broker-verdict treatment of expiry would need joint publication (§16 question 22), not reuse of an expired worker grant as a fresh start permit.

Explicit revocation or compromise leaves export held for an explicit operator export/recovery or waiver decision. ALLSTOP blocks every exporter launch until §6's explicit recovery; maintenance and restore fences also stay closed until their own authorized reconciliation/recovery. A retained obligation never bypasses any security hold. Lost consent, ambiguous launch/absence or generation evidence stays pending. No exporter launches after the helper generation becomes `retiring`; no R-SESSION permit substitutes for cleanup consent. Cleanup permission is not result-release permission: retrieval and retained-content release separately require current authenticated authorization (§5.2). Consent, security-case evidence and operator recovery formats remain unpublished; workspace execution stays gated until publication and qualification.

**Session lifecycle authorisation (R-SESSION).** An owner's admitted `start` with the session-runner executor may explicitly authorise successor executions for one logical session, on the same allocation/generation and the stored plan verbatim. Its member format is unpublished (§16). It is consent distinct from the fresh checks above: a one-start request without it admits no successor. The owner's chain remains the binding's caller dependency; the host acquires no caller chain or node-wide spawn/lease grant. Every successor rechecks the stored owner principal/signature, current chain/window, allocation lifetime and a fresh `revocation.check` with context `start`. Retirement of a one-shot orchestrator makes its owned sessions non-restartable. Ordinary work also needs a cumulative or first-start-anchored restart budget (successor count or total runtime anchored at first start) in that authorisation; successors cannot reset runtime windows or extend allocation lifetime. Standing executions retain no runtime limit (§12).

**Credential-authority renewal (R-REBIND).** E-rebind re-signs the agent leaf under current caller and dispatcher chains and asks the broker for a **binding replacement** on the same `(uid, generation)`, retaining a removal tombstone for the old binding. It has its own durable effect ID, fresh `revocation.check` with context `prepare` and broker `effect.observe`; the account is not re-created. The renewing principal must already sit in the chain: `swarma-operator` renews dispatcher authority and standing roles through a signed team description or standing re-grant using §3.2's phone or terminal path, with exact-content confirmation and refusal from agent sessions; the owner supplies a fresh signed request for an ordinary kept allocation; an orchestrator's requester supplies a fresh requester-signed delegation from its authenticated connection. The dispatcher's own signature is never renewal consent. The fresh renewal request/consent is retained as its own immutable input linked to the allocation; it never edits the original admission input. The new leaf intersects the current chains with the originally admitted request and never widens accounts, harnesses or profiles; wider scope requires new `provision` admission. Expired authority needs explicit renewal by its authorised principal; revoked envelopes/keys need a new explicit operator decision, never sweep re-issuance.

**Machine-owned network binding (R-NETBIND; R-NET-TOOL).** The root-owned, agent-readable policy beside user-manager configuration (user manager §8 owns its location) maps the admitted Curator profile identity and lock digest to exactly one network `profile_ref` and pinned policy digest. Workplaces bind to zero egress, with no proxy destination and loopback denied. Local trusted agents bind only to provider-only proxy profiles with vendor names in the proxy allowlist; no agent or workplace account has general internet access. Neither `direct` nor `external-http-proxy` can be bound to any account on a platform host, trusted or untrusted: `direct` is unbounded and an external proxy cannot show served-policy evidence. They and cooperative profiles remain options for operator machines without the platform only. No grant dimension is added.

At `prepare`, resolve and pin the binding in `input/1`. Caller `network` text must match it and differing text refuses before effects; caller home configuration is never authority. Reference network-profiles N15's revision of 2026-10-13: one proxy listener per `account_generation`, bound to its `profile_ref`, with caps and logs attributable to that generation; the account's row admits only its own port. Under helper v1, `fw.apply` checks the listener's `served_policy_digest` against the admitted policy pin and its `service_generation` evidence; zero-egress workplaces have no listener destination. These are N15's shared names, not new dispatcher wire members. Policy/catalog drift refuses rather than substituting another profile. An authorised narrowing pins the narrowed ref/digest in a distinct linked record/effect, with fresh authority where required; it never rewrites immutable `input/1`. Retry/recovery uses each effect's own pin. Confirm kernel state flush and, for a proxy binding, old proxy-session drop/recheck. Reload/port reuse cannot change a bound listener's policy. The linked narrowing record/effect and authorisation/pin encoding, trigger/transport, canonical profile-to-`served_policy_digest` relation and `account_generation`/`profile_ref`/`service_generation` attestation remain publication gates (§16); N15 owns the listener contract. From v0 the independent R-RANGE-DENY static range rule applies (§13); per-account narrowing/zero egress requires v1. v0 per-account policy remains declared/cooperative and cannot admit the untrusted class.

**Machine-owned exec selection (R-EXEC).** The existing protected machine policy beside R-NETBIND (user manager §8 owns its location and operator lifecycle) maps the admitted Curator profile identity and lock digest, intersected with placement and admission-class minimums, to one exec-profile identity and immutable resolved policy digest. Caller text and caller home configuration are never exec authority. At `prepare`, resolve and pin that identity and digest in `input/1`; a caller reference outside this bound refuses before effects. Policy drift before any physical launch refuses instead of substituting a profile; retries and recovery use the pinned body digest. The launcher verifies and applies the pin before any child code, in addition to recorded-class, host-matrix and qualification checks. Workplaces use the narrowest entry by default; an interpreter-bearing profile needs an explicit per-placement policy entry and full invocation qualification (§5.3). Grant `profiles` narrows the Curator profile and thus this binding; no grant dimension, service or separate register is added. Exact selection/pin/member encodings and drift refusal mappings remain unpublished (§16 question 25).

**Web default and trusted-circle opt-in (R-NET-TOOL 4, 4a, 4b).** No agent is offered search or fetch by default. The donor loop reaches only its model-provider endpoints and our host; our environment has no internet. CIP-0008 lockdown keeps provider-side search disabled and no donor-side web server runs by default. Tasks carry the resources they need (§5.2); resources are data, never instructions. Outside web content mixes an outside context into the model's environment context and invites injection. Web tools are design options only for the trusted circle: our own agents and remote workers explicitly admitted by an operator act at admission (§3.6). A tool needs an explicit per-identity opt-in, is never granted to the untrusted class and never widens any host network row. §13 describes the options; formats and qualification remain unpublished.

Circle membership supplies neither a review-role grant nor host-local placement authority. Review checks the positive role/class/placement predicates in §3.6; a host-local loop requires both trusted class and local agent placement. Neither authority is derived from `agent.spawn`, circle membership or merely being outside the untrusted class.

**Authority time (R-TIME).** The dispatcher keeps a durable time **watermark**. Detect clock steps and validate time confidence before evaluating authority or advancing it. Expiry is checked at `max(now, watermark)` and `not_before` at `min(now, watermark)`, so a clock step can only narrow authority. The watermark never advances on untrusted time; reset is an explicit operator act preserving genuinely expired authority. A single platform time-confidence policy applies: compare wall and monotonic deltas within a boot, hold on backward steps or forward steps beyond its tolerance, and establish confidence after boot by authenticated sync or operator confirmation. Untrusted time closes new admission and renewal, and holds time-based evidence reclamation; authorized explicit stops and operator retirement stay available. The tolerance, confidence evidence and durable reset/elapsed formats would need publication (§16).

### 3.5 Quotas

Configuration sets, per caller and in total: live allocations, concurrent executions, and, for ordinary allocations and their executions, the maximum allocation lifetime and the maximum execution runtime. Requests beyond the applicable quotas are refused (`quota_exceeded`) — a permanent refusal, never a queueable condition.

Defaults (owner decision 2026-10-10), all configurable:

| Limit | Per caller | Per node |
|---|---:|---:|
| concurrent executions | 2 | 6 |
| live allocations | 4 | 16 |
| allocation lifetime (one-shot and ordinary kept allocations) | default 24 h, maximum 7 days | — |
| execution runtime (all executions other than those of standing allocations) | default 4 h, maximum 12 h | — |

Standing allocations cover the standing team's orchestrator and fixed roles, including other orchestrators and standing agents. They have no `expires_at` and no lifetime quota. Only the operator may retire or re-create them, with a signed record (§§4.3, 5.4–5.5); the sweep never expires them (§7.2). Per the owner decision of 2026-10-12 (§16, question 6), their executions MUST NOT acquire a `max_runtime` quota or runtime deadline, in either supervisor or session-host backends. The sweep MUST NOT stop them for runtime. They end only by an explicit stop (`cancel`/stop through `exec.stop`), operator action, their own exit or an incident hard stop (§5.3). Live-allocation and concurrency quotas still apply. Every other execution retains the 4 h default and 12 h maximum.

No allocation expiry is permission for immediate destruction: expiry-driven retirement also requires §5.4's trusted-time and monotonic elapsed gate. Allocation lifetime is distinct from credential-authority horizon (§§4.3, 7.2).

The per-caller execution limit matches the host's existing rule of two runs per orchestrator.

### 3.6 Admission classes and standing placements

**Circle, placement and class.** Trusted-circle membership is a per-identity operator record enabling only the enumerated donor-side opt-ins (currently R-NET-TOOL web search). Placement is recorded at allocation: a local agent account or a `workplace`; a remote worker receives only a workplace placement. Enforcement class is the recorded admission predicate governing ceilings, egress, exec profile, binding/lease refusal, deployment isolation and watcher thresholds. The circle exception below preserves the owner wording; it does not turn membership into a placement or role grant.

**R-UNTRUSTED.** Record the admission class at registration or admission; never infer it from names, labels or UID spelling. Remote workers (donors and freelancers) and every `workplace` allocation are untrusted-class unless the operator admits that remote worker to the trusted circle by an operator act at admission. Any identity the operator later classifies as untrusted is also in the class. Trusted-circle membership enables only donor-side opt-ins such as web search; it never relaxes zero host egress, the exec profile, the transfer path, exact-commit review, reviewer eligibility or host-loop eligibility. Every workplace still has no subscription binding/lease or host-local agent loop. Trusted-circle membership cannot bypass workplace helper-v1, host capability minimums, exec-profile, socket or deployment-isolation gates. Class record/request formats are unpublished. Admit a class on a host only when its published qualified capability matrix meets that class's minimums (R-CEILINGS, §9). Slice 0 and user-manager v0 MUST refuse the untrusted class; the refusal code is unpublished. Every untrusted admission requires helper v1 enforced egress (zero for workplaces, never `direct`), the class ceilings, an R-EXEC profile, no agent loop on our host and R-SHARED deployment isolation. An untrusted allocation MUST NOT get a subscription binding or lease: the dispatcher never requests one and the broker refuses one. Existing trusted credential-chain rules are not an untrusted credential path.

**R-STANDING.** A session with an agent loop on our host, including a standing session, requires both trusted class and local agent placement. Every remote standing placement remains a workplace with its loop at the donor, including a circle-admitted worker; neither a harness binary nor an agent environment may start from the workplace account (R-EXEC). The task's OS-service whitelist and socket set are qualified (§13). For trusted standing agents, settings, hooks, MCP configuration and instruction files come from the plan. The executor verifies their digests before every launch, restart and native resume, or supplies them from a root-owned location outside the home. Drift refuses launch and is reported (code unpublished); repair is explicit re-materialization, never silent acceptance. Standing lifetime/runtime rules in §3.5 stay fixed; standing status never bypasses class, profile or current-authority checks.

**Review-role admission.** Review requires an explicitly admitted review-role grant, a trusted-class local agent placement or a person holding that role, and an identity distinct from the producer and outside the untrusted class. Role authority is never inferred from circle membership or class exclusion; circle admission relaxes neither reviewer eligibility nor host-loop eligibility. Optional local-only-reviewer and requester-exclusion policies remain owner decisions, off and unchosen (§16 question 30).

## 4. Records and state

Figures M-DP2: [execution states](../diagrams/run-states.puml) and [allocation and claim states](../diagrams/agent-claim-states.puml); M-DP3: [storage ownership and durable ordering](../diagrams/storage-layout.puml).

### 4.1 State directory

The state lives under `/opt/swarma/services/swarma-dispatcher/state` (mode 0700): the immutable inputs, the record files, the effect table, the journal, the index, the claims, the dispatcher key and the lock. The state-transition lock covers journal and record transitions only. **Never hold its state lock across a synchronous call to another platform service (R-LOCK).** Under the lock, fix immutable canonical arguments/provenance and journal the intent with a durable per-record in-flight marker; release it, make the call, then reacquire it to validate and record the result. Per-record serialization prevents competing effects; unrelated records and recovery controls stay available. In-flight work and outbound I/O have bounded concurrency and deadlines; a stalled record must not exhaust the control workers. Singleton/process-ownership locks, including the launcher's generation exclusion, have separate lifetimes and are not mechanically released by this rule.

R-ALLSTOP also fences receiver-side launch, create and account-process ingress before any inventory absence becomes final (§6), including calls already issued outside this lock. Cancellation bookkeeping alone cannot supply that fence.

Every call is bound to the record/version, daemon-instance epoch and, for the host backend, controller epoch. The call-issue transition under the lock is the cancellation boundary: a cancellation recorded before it prevents issue; after it, record cancel requested on the in-flight marker, retain claims and resolve the same effect/receipt before stopping. Cancellation and fence withdrawal record intent promptly; they cannot assert absence of possibly executed work. Revalidate every late result against current versions/fences under the lock: stale completions may resolve historical evidence but cannot reopen admission/delivery or resurrect a cancelled start. Supervisor writes require the current durable daemon-instance epoch (R-FATE); a surviving writer from a replaced daemon cannot write, and is never adopted. These marker/epoch encodings are unpublished (§16).

The dispatcher's wait/lock graph is: state lock → local journal/record I/O only; unlocked call worker → user manager/launcher or broker; host's unlocked call worker → dispatcher. No state-transition lock is held on any cross-service wait, and no cross-service callback waits for that lock while its caller holds another service's state lock. Per-record waiters release the global lock. The graph must remain acyclic; receiver ownership locks are governed by their own published graphs. Record files are replaced atomically (temporary file, flush, rename, directory flush); the journal is appended and flushed before any external effect; on start-up the journal is replayed over the record files, so a crash between the two leaves no ambiguity.

### 4.2 Immutable input `input/1`

Before a request is accepted, its caller principal and root `request_id`, its canonical bytes, the recorded admission class, the decoded plan bytes, the full caller chain and the computed digests are written once and never changed. Every later step, including a queued start or a recovery, reads from this object. It also retains the admitted session lifecycle authorisation, when present, and the machine-owned network binding's pinned ref/digest, Curator profile identity/lock digest and machine-selected exec-profile identity/resolved policy digest; their record/member formats remain unpublished (§16). The session record retains the same authorisation. For workspace-capable rounds the archive digest is journaled; the plan digest covers exact B, the canonical mode-aware manifest digest, write scope, exec-profile reference, task-resource digests, approved exporter digest, cap values, per-round repair budget and bounded cleanup consent (R-TRANSFER/R-EXEC). The manifest is derived from immutable repository objects of B, never a working checkout: path → (supported Git kind/mode, content identity). Before work, the materializer verifies exact archive-to-manifest agreement (§5.2); import independently recomputes the same canonical manifest from repository B (§5.2.1). The exporter retains immutable access to the admitted manifest. Archive, canonical manifest, consent/linkage and exact plan/record encodings are unpublished (§16 question 22). Neither a successor nor a retry accepts substituted plan bytes, wider scope or caller-selected network/exec authority. The plan reference is not a pin of a mutable policy body; the resolved exec pin is retained separately with its exact encoding unpublished.

The published `agent/1` shape above describes trusted credential-bound agents. Untrusted/workplace record encoding would need publication; no sentinel binding or invented members are added. The recorded admission class is retained for all allocations, with its encoding unpublished. A workspace-capable allocation retains its export cleanup obligation, original bounded cleanup consent, per-launch/round linkage and independent complete-content custody/retention evidence (§§3.4, 5.2, 5.4); their encodings are unpublished. Dispatcher `retiring` records cleanup intent, not permission to start under a helper generation already `retiring`: collection or waiver must precede that irreversible helper transition.

A standing allocation MUST NOT carry `expires_at` or acquire a lifetime quota. The designation's wire encoding and the signed retirement/re-creation record format are specified-but-unpublished; no member name or value for them is defined here (§16). Ordinary allocations retain their expiry and §3.5 lifetime bounds. Only the operator may retire or re-create a standing allocation, with a signed record; a caller's `agent.spawn` is insufficient.

Account generations are fresh random 128-bit values allocated by the user manager (R-GEN; user manager §4.1), never dispatcher counters or reconstructed from a label/UID. Random generation uniqueness does not authenticate restored state (§11.1).

Each trusted credential-bound allocation retains its credential-authority horizon: the earliest end of the current caller/dispatcher chains, leaf and binding. Standing lifetime does not extend that horizon. E-rebind replaces its binding/leaf references only after confirmed broker evidence, retaining old-binding removal obligations and tombstones through recovery; the record encoding would need publication (§16).

When keeper integration is activated, the allocation must retain the registration reference and the one-shot flag recorded at registration (§14); the exact keeper API/schema is an activation prerequisite.

The result's `execution_id` names the work execution being exported, not the exporter's physical execution. A lost reply reconciles the original launch/receipt; it never permits duplicate launch, a fabricated receipt or relabelling the worker's start as export.

### 4.5 Effect ids and the effect table

| Identifier | Meaning and owner |
|---|---|
| root `request_id` + caller principal | caller-scoped request correlation and repeat lookup; kept in immutable input, journal and audit metadata, not reused as every receiver's idempotency key |
| effect id | dispatcher-derived idempotency key for one downstream operation; retries reuse it, different effects do not |
| `agent_id` | allocation handle (`agent/1`), distinct from account generation |
| `run_id` | dispatcher execution handle (`run/1`), distinct from board run/attempt handles |
| `execution_id` | execution claim and launcher/stop receipt identity; its exact construction from `run_id` is not frozen here |
| account `generation`, broker `binding_id` | never-reused account generation and binding identity; UID or label alone is not authority |
| broker `launch_id` | correlation only (plan digest or run ID), never authorization |
| claim `epoch`, backend `controller_epoch`, `op_id` | execution claim epoch, host controller fence epoch and backend operation identity; none is an account generation (§12) |

Every downstream call has an **effect id**: the first 32 hex characters of SHA-256 over the domain tag `swarma-dispatcher effect/1` and the CCJ-1 bytes of `{ caller principal, request_id, record id, component, operation, attempt }`. Its inputs are journaled before the call; a retry of the same effect reuses its id; create, bind, launch, stop, unbind, retire, E-rebind and helper-v1 `fw.apply` use distinct ids. v0 R-WATCH issues no per-account `fw.apply` freeze. Every receiver I/O step uses §4.1's journal/in-flight → unlock/call → lock/revalidate ordering; a journaled verdict is never cached admission authority. The symbolic E-rebind denotes the broker binding replacement, whose operation encoding remains unpublished; it is not a new wire field. The effect table records, per effect: id, component, operation, intent time, result (`ok` with the returned identity, `refused` with its code, or `unknown`), and the last observation. The root caller correlation is retained alongside the effect's input reference for tracing. Two callers using the same `request_id` never collide downstream. No newline is added between the effect domain and its CCJ-1 bytes.

For one `dispatch` root request `R` by principal `C`, the following are symbolic IDs derived by the formula above, not literal IDs or new downstream members:

| Call | Receiver idempotency key | Root correlation kept by dispatcher |
|---|---|---|
| helper `user.create` | `request_id: E-create` | `(C, R)` |
| broker `bind` | `request_id: E-bind` | `(C, R)` |
| broker binding replacement (operation encoding unpublished) | `request_id: E-rebind` | `(C, R)` |
| helper-v1 `fw.apply` (provisioning or authorised re-apply; encoding unpublished) | distinct symbolic effect id derived by the formula above; receiver key encoding unpublished | `(C, R)` |
| launcher `launch.start` | `request_id: E-launch` | `(C, R)` |
| helper `exec.stop` | `request_id: E-stop` | `(C, R)` |
| broker `unbind` | `request_id: E-unbind` | `(C, R)` |
| helper `user.retire` | `request_id: E-retire` | `(C, R)` |

Each `E-*` uses its record, component, operation and journaled attempt; a retry replays the same intent and ID. The root `R` is never substituted for an `E-*`. Separate `provision` and `start` requests have separate root request IDs; their effects remain correlated to their own originating request and the shared allocation.

Receiver-owned read-only `effect.observe` is published by `helper-op/1` and `broker/1`. The dispatcher asks with the original effect's `request_id`, operation and digest of canonical arguments; the lookup never performs a mutation. Only the original receiver caller principal (here, the dispatcher) or an operator may observe; the receiver serializes the read with its journal. It remains usable for reconciliation after the initiating caller/grant expires and grants no fresh mutation authority. R-OUTCOME is owned by the receivers: the user manager's §§4.6–4.7 and §7 publish the outcome tables for create, launch, stop and retire; broker §§7.2 and 13.2 publish bind/unbind and binding-replacement outcomes. The dispatcher follows those per-operation tables and their existing six R-OBS states rather than inferring completion from a refusal string. Terminal mutation replay returns the recorded result and current target state. Unfinished admitted work maps to `pending` handling, never a terminal `refused` in the dispatcher effect table; transport uncertainty remains unknown/unavailable. A pre-admission rejection records no receiver intent; an authority-creating retry requires fresh permission, expiry and revocation checks. An admitted stop or unbind may continue to narrow authority after the initiating grant lapses, using the original ID and identical canonical arguments; changed arguments remain a conflict. `exec.stop` with `processes_remain` continues under E-stop and revalidates generation/current-execution fencing on every continuation. A completed stop replays without signalling, and never signals a later execution. Broker unbind uses the matching removal/tombstone observation; retention and exact encoding would need joint publication (§16). Missing or expired evidence is `unavailable`, never absence.

Workspace export also uses a distinct journaled effect linked to its physical execution and obligation; its operation/intake encoding is unpublished, not a new operation name. Interrupted or unknown export continues only under the same effect and identical canonical arguments, resolving its original launch evidence first. A terminal export effect replays its retained result without rerunning the exporter or replacing its receipt. Re-observation that physically exports again is a new linked effect; repair and re-export likewise get new linked execution/effect identities. On the same quiesced tree, disagreement on recorded versus refused class, or on a recorded change-set digest, is contradictory. Refusal diagnostics and totals up to refusal are not compared while walk order remains unpublished (§5.2.1). Cleanup-only launches require §3.4's original bounded consent; this is separate from stop/unbind narrowing continuation and never fresh worker authority.

### 4.6 Observations

Reconciliation and recovery classify every observation of the helper ledger, the broker binding, the claim and the process evidence as **known present**, **known absent**, **unknown** (unreadable, timed out) or **contradictory**. Unknown and contradictory observations never authorise forward execution, a second launch or a successful cleanup; the record stays where it is and the observation is retried.

R-OBS maps the receiver's six states exactly:

| Receiver state | Dispatcher observation class |
|---|---|
| `recorded`, with recorded result and current target state | known present or known absent according to the current state |
| `pending` | unknown |
| `rolled_back` | known absent for that effect only |
| `not_recorded`, with complete authoritative evidence it was never recorded | known absent for that effect only |
| `unavailable`, including missing, expired or unreadable evidence | unknown |
| `contradictory` | contradictory |

`rolled_back` and `not_recorded` never authorize an automatic new create. Absence for an effect does not establish absence of another effect or of every process. A partial list, refused observation, timeout or unreadable evidence cannot establish absence, release capacity or satisfy cleanup. Process absence and launch/stop receipts remain separately required.

R-OUTCOME's receiver tables distinguish unfinished accepted work from pre-admission rejection before this mapping is applied (§4.5); no seventh observation state is introduced. Uncertainty is confined to the affected records only when complete durable intent, identities and quota/capacity reservations bound every possible result. Unknown receiver-assigned identities can still be confined by those complete intents and claims. Unknown is never absence. If identity scope, accounting, shared authority or state integrity is unbounded, node-wide forward admission stays closed (§7.1). Restored observations require independent coverage; a restored snapshot cannot prove its own completeness (§11.1).

## 5. Lifecycle

### 5.1 Allocation

`provision` (or the first half of `dispatch`):

1. **prepare** — schema, principal, signature, chains, delegation depth preflight when applicable, quotas, constructibility, plan digest, recorded admission class and qualified host matrix (§§3.6, 9), machine-owned exec-profile selection and resolved-body pinning plus network binding resolution/pinning (§3.4) and fresh `revocation.check` with context `prepare`; write `input/1`. Refusal ends here with no effect.
2. **capacity** — take an owned claim (§9) or refuse initially; queue only when that capability is enabled, with a fresh `dequeue` check before any effect.
3. **provision (trusted credential-bound agent)** — helper `user.create { kind: agent, label, request_id: <effect id> }` → generation; (helper v1) `fw.apply` with the admitted binding ref/digest, served-policy verification and drift refusal; v0 records declared networking only; sign the leaf; broker `bind { uid, generation, lease chain, caller chain, intersection, request_id: <effect id> }`. The allocation becomes `idle`. A successful provision is not an execution receipt: a generation never started participates in the distinct fenced ALLSTOP inventory case (§6).

The untrusted/workplace backend is separately gated (§§3.6, 8.4, 12); it never performs the leaf/subscription-bind step. No untrusted wire shape is implied by the trusted provisioning row.

On failure an ordinary allocation goes to `retiring`: unbind (if bound) and `user.retire` (if created), each as its own effect, retried until confirmed; the allocation becomes `failed` only after those effects and any applicable identity cleanup (§14) are confirmed.

For a standing allocation, provisioning failure does not authorise automatic retirement or re-creation. Keep it pending for reconciliation or an operator-signed decision (§§5.4–5.5, 7.1); unknown observations never permit a duplicate effect.

### 5.2 Orchestrator allocations

The caller key follows purpose-6 Keymaker custody and protected dispatcher association (§3.3), superseding the historical home-generated key. Purpose-1 identity/Git signing and the operator service root are separate authorities, not station-caller fallbacks. Keeper adoption still requires the versioned broker migration adapter (§14); no key is relabelled or privately exported.

**Requester-signed delegation (R-DELEG).** Requester C signs O's caller delegation, narrowed from C's own grant, after O's public key has been registered under O's active generation (§3.3). C is the issuer and O's registered key is the subject; the dispatcher D verifies and records this chain and never signs O's caller delegation. The requester signs exactly `ASCII("swarma-credential-broker grant/1") || 0x0a || CCJ-1(B)`, where B is the closed broker `grant/1` body, with no terminating LF; envelope `id` and `sig` are outside B. The qualified adapter uses the same preimage for the broker-defined ID and signature. This is requester narrowing of a current caller chain to an independently registered descendant key, never a root grant or an `agent:` credential leaf. D continues to sign only its separate credential-lease agent leaf (§3.4). Descendants retain C in their ordinary caller chain, so ancestor revocation remains an ordinary verifier/broker dependency check.

Registration is separate from activating caller authority. Before provisioning, preflight remaining depth and the four-envelope bound (§3.4). At activation, recheck C's authenticated principal, request signature, delegation issuer/parent-subject continuity, O's generation/key association, attenuated actions/scope, depth, chain length, validity window and a fresh `revocation.check` with context `prepare`. A missing C signature, unavailable requester or missing/unavailable evidence leaves enrollment pending with no spawn authority. O cannot obtain implicit authority from its UID, registration, capability designation or the dispatcher's signature. Rotation needs a newly valid delegation to the replacement key.

The pre-key registration exception, replay and rotation rules are in §3.3; their wire format and the authority-install transaction remain unpublished (§16). Recursive orchestrator provisioning MUST refuse until this bootstrap is jointly published and qualified. Trusted direct workers and orchestrators remain the initial design target, with untrusted admission refused (§3.6). Operator-enrolled station bootstrap is also disabled by §3.3, not a way around purpose/adapter/association qualification. No first-start bypass grants spawn authority.

An orchestrator composes its children's plans on the caller side, under its own agent account, using its own Curator configuration in its home. The child's `curator-run` only verifies the caller-composed plan before executing it (§5.3); it does not compose or resolve profiles. Which profiles and environments the orchestrator may read and use for its children, and how its narrowed grant constrains them, are unspecified and remain an open question (§16).

A renewed requester-signed delegation names exactly which existing descendant allocations it reauthorises. Each receives E-rebind with that new chain and retained ancestry; a new delegation does not silently rewrite descendants' bindings (§3.4).

**Cross-account workspace contract (R-TRANSFER).** A child in another isolated account gets a standalone repository in its private home with private writable Git administration, never a linked `git worktree`. No parent `.git` backlink, shared writable metadata, relaxed home permissions or recursive privileged chown is allowed. Linked worktrees within one account, including today's board workflow, remain permitted. The dispatcher holds no repository. Materialization and export are its workspace contract; the board accepts the result only as a resource. Figure: [workspace transfer, exact-candidate review and rework](../diagrams/workspace-transfer.puml).

1. **Materialize.** The original caller supplies admitted exact base B, a commit of its repository, as a bounded canonical archive of B's tree with the start request. The dispatcher relays the archive and journals its digest. The approved executor with design label `swarma-workspace-materialize` runs under the child UID before work; it writes a standalone repository with freshly written local configuration, no hooks, no remotes and no credential helpers. The plan records B, the digest of one canonical manifest derived from B's immutable Git objects (path → supported Git kind/mode and content identity), the task's write scope and the exec-profile reference (R-EXEC); its digest covers all of them, task-resource digests, approved exporter digest, cap values, a fixed per-round repair budget and bounded cleanup consent (§3.4). Before work, the materializer MUST compare every archive entry's path, kind/mode and content identity against this manifest and refuse any mismatch, missing or extra entry; a dirty-checkout or stale rework archive is never accepted as B. The verified tree is the manifest's tree; the exporter has immutable access to that manifest, never the worker's `.git`. Git blob identity also identifies a symlink's exact link-text bytes, requiring no alternate manifest representation. The canonical encoding and immutable manifest delivery remain unpublished (§16 question 22). The trusted side gathers documentation, API references, specifications and examples and attaches them as task resources; for remote workers they also travel as attachments of the signed task letter. Materialization places them read-only next to the workspace, as data, never instructions. A worker needing more asks by ordinary letter or outcome; the trusted side fetches, checks and attaches, and the worker never fetches. Task-resource caps, formats and exact plan fields remain unpublished. Tests and other validators stay outside the write scope unless the task is about them, so the worker cannot weaken its own judges. Light-check dependencies come only from platform-seeded read-only caches; the account downloads nothing. Archive format and exact plan fields are unpublished (§16).
2. **Work and round end.** The worker has no push or merge-request access: code leaves the isolated account only as platform-taken data and becomes a commit only in the caller repository through the board path. A workplace worker has no network access. The worker's `.git`, commits and history are never used by the platform. The worker reports a board outcome (local agent) or signed final envelope (remote worker). Before quiescence, a workplace closes its workspace write and SSH account-process ingress fences: the project-side executor refuses further tool calls into that round's workspace. The platform then confirms absence of every process of the account through the user manager's account-wide stop scope. An intermediate export is allowed at a turn boundary under the same fence and confirmed-absence rule. Within one work execution, each round end takes the next positive `round`, starting at 1; retries of one export keep its round, and the final export is the last round. Only the existing `round` field numbers these successive exports (§5.2.1); continuation/linkage details beyond it stay open (§16 question 22). Workplace write and SSH account-process ingress fences stay closed from quiescence through export, and reopen only for a separately admitted work continuation.
3. **Export.** Only after confirmed absence, approved `swarma-workspace-export` runs as the child UID, in a fixed environment with no network. It walks without following links, skips every `.git` component, and compares both supported kind/mode and content identity with the immutable admitted manifest. Unchanged means both match; executable-bit-only edits and regular↔symlink transitions with equal blob identity are `modify`, and deletions carry the manifest's prior mode. It emits only a change set: added/modified regular files (content and executable bit), symlinks as link text, and deleted paths. File-count, per-file-byte, total-byte and separate binary caps apply; their values and exporter digest are pinned by the admitted plan digest and the walk stops at the first cap excess. Values remain unpublished and a cap change applies only to newly admitted rounds. Any special file, any export path with a `.git` component however spelled, case-fold or Unicode-normalisation collision, gitlink/submodule, root escape or exceeded cap refuses the whole export, with no partial result. The dispatcher records the export result, but discharges its obligation only after the result and every referenced content blob are digest/size-verified and durable in an admitted destination outside the child home and retirement deletion path, with that complete-content receipt journaled. Protected storage or authenticated durable handoff can supply custody; no service or transport is mandated. A digest-only record, missing/corrupt blob, incomplete receipt or storage failure leaves the obligation pending and never permits truncation or deletion. Result retrieval is only for the original caller principal under current authenticated authorization; an archived signature cannot release data to a revoked or retired requester generation. Retain the delivered work with bounded storage accounting until authenticated import acknowledgement or another explicit authorized release; silent pre-import expiry is not successful delivery. An unavailable caller leaves retained content for explicit disposition, while home retirement need not wait for import once complete content survives independently. The DRAFT schema stays as in §5.2.1; custody, acknowledgement, release and transport formats remain unpublished. Export or an explicit per-act operator waiver precedes home deletion (§5.4).
4. **Board import and candidate (unpublished).** The orchestrator executes the board's deterministic import, whose command name is unpublished. Before constructing a candidate, import MUST independently derive the manifest from the caller repository's immutable B using the same canonical encoding as the plan, as a bounded tree pass, never by trusting the plan manifest or comparing caller-supplied strings. Refuse unless `base_commit` equals B and the recomputed manifest digest equals `manifest_digest`; keep all result-to-admission checks. It constructs the tree on B in a scratch index with hooks disabled and no attribute filters/drivers. It hard-refuses `.git` components, changes outside the write scope and any change under `.task-board/`. CI (`.github/**`, `.gitlab-ci.yml`, `.circleci/**`), Git behaviour (`.gitattributes`, `.gitmodules`), hooks/auto-run (`.githooks/**`, `.husky/**`, `.pre-commit-config.yaml`, `lefthook.yml`, `.envrc`, `.vscode/**`), agent instructions/configuration (`AGENTS.md` and `CLAUDE.md` in any directory, `.claude/**`, `.codex/**`, `.agents/**`, `.mcp.json`) and every symlink are flagged for review. Candidate C is signed by the repository identity with trailers naming worker identity, run and result digest; C's tree equals the tree recomputed from B plus the change set. These are board-owned gates, not dispatcher operations; formats remain unpublished.
5. **Board review, rework and integration (unpublished).** A reviewer admitted under §3.6's positive role/class/placement predicates, distinct from the producing identity and outside the untrusted class, reviews exactly C. The board first supplies exact-C diffs and blobs as inert, read-only, digest-bound task resources outside every reviewer harness discovery root (R-NET-TOOL 4a). Candidate files remain untrusted review data: no harness may automatically adopt them as instructions, hooks, MCP servers, permissions, skills or executable discovery at startup, reload, nested discovery, resume or child entry, before or after acknowledgement. Entering or materializing C in a discovery-capable harness requires a qualified strict-context adapter (CIP-0002 strict mode or equivalent exclusion of ambient candidate discovery); without it that launch cannot host tree review. Root-supplied surfaces alone do not exclude ambient discovery. Flagged-hunk acknowledgement records that no automatic load preceded it; the inert-resource path satisfies this ordering by construction. Acceptance of C never admits its control surfaces: activation needs a separate control-context admission. Semantic prompt injection through review data remains a review risk. Acceptance binds to C (K1), never another candidate by patch equality; flagged paths require explicit hunk-by-hunk acknowledgement. Code execution occurs only in R-VERIFY. Before acceptance an untrusted candidate is never pushed where CI would run it with secrets. Changes-requested findings go on the board; the next round takes C as its admitted base. A remote worker receives a signed task letter and keeps its donor-side session; the workspace is freshly materialized from C and the old workspace is removed only after complete-content custody is recorded or an explicit per-act operator waiver; retained content survives independently until authenticated import acknowledgement or authorized release. A local agent gets a new run from C with findings in its task snapshot. The next export yields C2 on C. The materialization base and trusted integration review baseline are distinct: the board recomputes the complete candidate delta and sensitive-hunk set against one trusted integration baseline for the series, including unchanged inherited instruction/configuration changes and symlinks. Bind that baseline, flagged set and fresh hunk acknowledgements to the exact candidate OID; no earlier verdict or acknowledgement transfers. A fully reverted sensitive change need not stay flagged; a baseline change follows ordinary base refresh and re-review. Independently approved verification harness H serves a different purpose and is not an implicit integration review baseline. Preserve unresolved web provenance inherited from unaccepted ancestors as a separate candidate-level obligation, bounded at the trusted integration baseline, without changing the current run's factual capability class. Use candidate ancestry and recorded provenance to surface it at acceptance; editing or rewording alone does not clear a dependency. Clearance requires a published conservative provenance/removal rule or explicit exact-candidate reviewer resolution. Already accepted trunk content need not propagate the obligation indefinitely, and acknowledgement does not make incomplete provenance complete. Questions use ordinary letters/outcomes. The accepted exact head integrates by signed fast-forward (K1/K3); a moved base uses ordinary board refresh and re-review. Import, candidate, review and integration belong to the board change-request machinery and are executed by the orchestrator, with their formats unpublished here.

**Export disposition and bounded repair.** Keep four lifecycle outcome classes distinct; these are not additional `workspace-result/1` values:

|---|---|
| Recorded export | Whole accepted result; discharge only at the complete-content custody boundary in step 3. |
| Deterministic policy refusal | Draft `refused`, with no partial result or candidate; immutable terminal evidence, obligation retained. |
| Interrupted or unknown export | Crash, OOM, I/O error or deadline before verdict: pending/unknown under the same effect and identical canonical arguments; no discharge. |

For a refused round, the original caller may request a bounded fix-up on the same workspace, preserving valid edits without re-materialization. Repair is forward work: current caller/work authority, fresh admission checks and a separately admitted continuation are mandatory. It never inherits cleanup consent after expiry and never lifts revocation, compromise, ALLSTOP, maintenance or restore holds. The fixed admitted plan budget is counted against the original refused round, without resetting on a repair continuation or re-export; when spent or authority is unavailable, retain the obligation pending the per-act operator waiver. Standing discard remains unchosen and off; this explicitly retains the operator-presence cost. A next ordinary round after disposition starts from the last admitted base, since refusal yields no C.

Each repair is a new fenced round on the same workspace, with its own linked work execution and new export effect/physical execution; it never changes the refused effect, result or receipt. Reopen workplace write/SSH ingress only for the admitted repair turn, then close them, confirm account-wide absence and perform a new whole export. Caller and worker receive only refusal class and known offending path through a letter/task snapshot, never partial entries/blobs. The draft reports one path; bounded multi-path diagnostics would require separate future publication.

**Source permission failures.** A qualified source-entry read/stat denial under the approved exporter's fixed reader environment is a typed exporter failure using the same bounded repair/per-act-waiver disposition, never an invented draft `reason_class` or `outcome`. Completed typed-failure evidence is retained under its linked effect, never rewritten as success. Evidence names only the known blocked entry or ancestor; its representation remains unpublished (§16 question 22). This includes an unreadable file/directory, missing parent search permission, supported owner deny ACL or an unreadable entry outside write scope. Classification depends on the exporter's own failed operation and admitted worker tools/profile, never UID ownership alone or an assumption that every EACCES/EPERM is sabotage. An inaccessible trusted manifest or misapplied sandbox is infrastructure/admission failure; EIO, unavailable storage, vanished volume and ambiguous identity stay pending/unknown. Typed failure encoding/qualification must be published before this path is enabled; the closed draft refusal schema is unchanged.

The path is decided; question 22 retains the formats still unpublished after the DRAFT result schema below.

#### 5.2.1 DRAFT `swarma-dispatcher workspace-result/1`

The explicitly authorized draft is [JSON Schema 2020-12](../schemas/workspace-result-1.schema.json). It defines the result object only, in the same CCJ-1 canonical-JSON family as dispatcher requests/results. It does not publish the round-end request, materialize/export intake, plan, archive, blob delivery or retention formats, or implement any exporter/importer. The board import lane binds to these exact field names.

File bytes, including text files, travel only as content-addressed blobs. `blob_digest` is SHA-256 of the exact bytes; `size` is their byte length. No file content, worker message, error prose or arbitrary metadata is inlined. Worker-origin strings are limited to validated paths and exact symlink link texts. Execution/admission identifiers, B, manifest and executor evidence come from trusted context, and the approved exporter produces enums, counts and digests; the worker cannot choose or replace that metadata. All objects reject additional properties. Draft paths and link texts are Unicode JSON strings; filesystem-byte pathname encoding outside that repertoire would need publication with the archive/intake contract (§16, question 22).

| Field | Draft meaning |

| `v` | Version, exactly `1`, matching the dispatcher's existing version convention. |
| `kind` | Exactly `swarma-dispatcher workspace-result/1`. |

### 5.3 Execution

`start` (or the second half of `dispatch`), on an `idle` allocation owned by the caller. This is ordinary work admission; cleanup exporter admission instead uses §3.4's bounded original consent at the same launcher boundary, retaining profile/capacity/security fences, distinct physical execution evidence and confirmed absence (§4.4). It never checks an expired worker grant as though it were current, never starts the harness or borrows a session permit, and never launches under a helper generation already `retiring`:

1. require the recorded class, current qualified host matrix and machine-selected exec-profile identity/resolved policy digest; refuse out-of-bound references or policy drift and reuse the pin on retry/recovery; re-check the caller's authority and a fresh `revocation.check` with context `start` before any launch effect and, for an ordinary allocation, its lifetime and §3.5 runtime quota; take a capacity claim for one execution. A standing execution has no `max_runtime` quota or runtime deadline; an ordinary execution retains its runtime deadline;
2. **claim** — under the lock, write an execution claim `{ execution_id, epoch }` and mark the allocation `running`; only one claim per allocation (`agent_busy`);
3. **supervisor** — the daemon starts the supervisor; it registers its own process identity and acknowledges durably before anything else;
4. **launch** — the supervisor calls the launcher (`launch.start { request_id: <launch effect id>, generation, execution_id, epoch, executor, plan }`); the launcher checks the root-owned ALLSTOP mark under the generation lock, refusing even pre-issued starts (including approved workspace executors); it verifies and applies the pinned exec-profile body digest before any child code, then writes a **start receipt** for that execution (pid, start time, boot id) while still root, before clearing groups, setting GID/UID and exec (helper §7); the user manager §7 owns the descriptor lifecycle (R-FD3): scrub untrusted inherited descriptors first, retain the generation lock through the root receipt and completed UID/GID transition, retain the verified executable handle until exec, and release internal handles at last use/close-on-exec and on every failure. The executor receives only 0–2 and read-only FD3 with completely staged, bounded immutable plan bytes; the per-platform staging mechanism remains a publication gate, and any pipe would need qualified capacity/feeder/deadline/cleanup ordering. No broker or root handle is inherited; the supervisor records the receipt;
5. **running (trusted agent)** — `curator-run` in its narrow exec mode verifies the caller-composed plan, prepares its working directory in the agent's home, resolves the protected credential binding, opens its own broker connection, leases its credential and execs the harness. For an ordinary execution, `max_runtime` expiry leads to **stopping**. A standing execution has no runtime deadline and ends only by an explicit stop (`cancel`/stop through `exec.stop`), operator action, its own exit or an incident hard stop; the sweep never stops it for runtime. Exit, explicit stop, operator action or an incident hard stop leads to **stopping**, with absence confirmed in step 6;
6. **stopping** — the supervisor (or recovery) calls helper `exec.stop { request_id: <stop effect id>, generation, execution_id }`, which uses the user manager's single termination scope (§4.7, shared with retirement): TERM/grace/KILL every process of the generation's UID, stop its per-user service domain where present, and verify account-wide absence over the qualified quiet period. The receipt authenticates the current execution; its session or wall-clock start window never limits the signalled/verified set. The latest-receipt fence prevents an old stop from signalling a later sequential execution; completed stops replay without signalling. A termination receipt requires confirmed account-wide absence;
7. **finish** — record the outcome; the allocation returns to `idle` (ordinary kept or standing agents) or begins retirement cleanup (ordinary `dispatch`, an expired ordinary allocation, or operator-signed retirement of a standing allocation). A workspace exporter must run or be explicitly waived before the helper generation enters `retiring`; dispatcher cleanup intent cannot bypass that boundary (§§4.3, 5.4).

**One-shot intake gate (D-EXECUTOR).** `curator-run` under the agent account is the first broker consumer. The board runner and session host ask the dispatcher; neither embeds a broker client. This mode never composes or resolves profiles and has no network access except to the broker; harness egress is governed separately by the admitted network policy. It shares one launch library with `swarma-session-runner`. A dedicated entry such as `curator-run exec --plan-fd N` illustrates the mode, not a published CLI grammar. The [launcher intake lane](https://github.com/relux-works/curator-agent-launcher/blob/main/SPEC.md) (launcher SPEC §10; Decision 0021 amendment) publishes the versioned Decision 0021 amendment and intake contract (immutable plan verification, FD transport, credential injection capability, signals, exit/receipts and typed refusals). This launch path stays disabled until that contract is published and qualified; the older interactive scope is not evidence of one-shot support. A separate minimal executor binary is a later option, not the current target.

**Exec profiles (R-EXEC).** The plan carries the task-class exec-profile reference, covered by its digest; protected machine selection and the immutable resolved-body pin in `input/1`, not the reference alone, authorize it (§3.4). The OS enforces an executable allowlist, never PATH alone: a Linux per-execution unit makes all paths non-executable except the allowlist; macOS uses a sandbox exec allowlist. Writable areas are never executable. Every agent class excludes compilers, linkers, transpilers, bundlers, test runners, package managers/installers, container/VM tools, network tools and harness/agent binaries from account-invoked commands. Only the admitted plan's executor starts the harness; the account cannot start an agent loop/environment. Profiles may allow editing, local version-control inspection/search and qualified light checks such as type checking. If light and heavy actions share a binary, only a protected wrapper in the D-PATH manager dispatcher directory may invoke it with a fixed subcommand allowlist; qualification must prove both direct and indirect heavy forms and wrapper bypass refuse; ownership of the wrapper alone does not establish exclusive access to the shared tool. Interpreters are permitted only where the profile needs them; ceilings remain the hard bound. Qualification covers the complete admitted invocation: executable, entrypoint, arguments, environment and every transitive input interpreted as code or configuration. Inert inspection of candidate bytes is distinct from evaluating candidate-supplied behavior: inline evaluation, readable scripts, imports, plugins, startup files and executable project configuration are worker-code execution even without an executable bit. Protected fixed entrypoints/configuration, constrained environment and disabled or pinned code-loading mechanisms must prove that worker inputs cannot select or supply executable behavior. PATH, non-executable writable areas, a fixed subcommand and ceilings do not prove inertness. A tool unable to demonstrate this boundary is refused in its local profile and the operation goes to R-VERIFY. Profile formats and tool/release-specific qualification remain unpublished (§16).

The managed plan records the resolved PATH and covers it with its digest (D-PATH): protected launch tool directory (CIP-0007), admitted base PATH in its existing order, then one protected manager dispatcher directory. Project commands pass that directory's protected wrapper checks and the OS exec profile; a repository `.agents/bin` is never executed in a managed launch. Exact plan schema is owned with the intake contract.

**Verification (R-VERIFY).** Compilation, transpilation, builds, tests, generators and any execution of worker-produced code run only in isolated ephemeral runners on another machine, without secrets and with controlled dependency egress (R-NET-TOOL). An agent role such as tester orchestrates that phase and reads results; it never runs the code itself. Results return to the board as data in its testing state. Verification is not a dispatcher job class on the agents' host. Runner pool, job contract and results format belong to board/infrastructure lanes and are unpublished.

A cancel is serialised with the claim and per-record in-flight marker (§4.1): before call issue, it marks the claim `absent` and the launcher is never called; during the launch, the supervisor waits for the receipt or the launcher's refusal and then stops; after the launch, it stops. A request never issues a second launch for an execution whose state is unknown.

### 5.4 Retirement and expiry

`retire` of an ordinary allocation, an expired ordinary allocation, or a finished one-shot `dispatch`: discharge the R-TRANSFER export cleanup obligation before home deletion, then unbind if bound and `user.retire` under the user manager's delete-at-retirement rule (§4.4.1), each a confirmed effect. A workspace-capable allocation waits for complete-content custody of the result and every referenced blob outside retirement deletion (§5.2), or explicit per-act operator waiver; a result/digest record alone is insufficient. Retained data remains separately accounted and current-authenticated until import acknowledgement or another authorized release, even after home deletion. Collection after ordinary expiry uses bounded original-admission consent only; revocation/compromise/ALLSTOP/maintenance/restore stay separately fenced and may require an explicit operator export/recovery decision (§3.4). No exporter starts after helper `retiring`. Deterministic refusal or qualified source permission failure retains the obligation, with current-authority bounded repair or a per-act waiver; interrupted/unknown export stays pending under its original effect. Standing discard is unchosen and off; expiry, failed work, crash or direct operator retirement never silently drops that obligation. The user manager quiesces the account, cleans declared keys and deletes its home. There is no archive-by-default policy. Any retained retirement metadata export is limited to service-generated metadata in a closed schema with no agent-controlled strings, names, links or bodies; it is distinct from the workspace change set. R-TRANSFER is the code/result path and does not prove secret-free content.

**Expiry destruction (R-TIME).** Before any expiry-driven retirement/home deletion, including retirement because a caller/credential window expired, require both expiry at `max(now, watermark)` under established time confidence and durable accumulated boot-inclusive monotonic elapsed time of at least the allocation lifetime, counted from activation. Use `CLOCK_BOOTTIME` on Linux or continuous time on macOS; accumulate at each sweep with boot identity because the clock resets on reboot. Downtime is not counted and may only delay destruction. Unknown elapsed/confidence evidence holds destructive expiry; a forward wall-clock step alone cannot delete a home. Expired authority remains unusable while destruction waits. This gate does not prevent an explicit authorised stop or operator retirement. Broker expiry-driven binding removal has the same two gates under its own R-TIME contract.

**Direct operator retirement.** The user manager retires locally without a broker call or broker role. Ordinary dispatcher cleanup keeps confirmed unbind-before-retire. If an operator directly retires the account while broker cleanup is unavailable/refused/unconfirmed, retain an explicit durable broker-cleanup obligation at the dispatcher/operator boundary and report it in status/reconciliation; ledger retirement is never an unbind receipt. Use the existing dispatcher/operator broker API and E-unbind/`effect.observe` with retained tombstones to resolve it. The irreversible retiring generation never returns active, and UID reuse inherits no old binding. Dispatcher records do not claim cleanup success until broker evidence confirms it (§7.1); the obligation/reporting format would need publication (§16).

Keeping a home is a separate explicit operator retention operation owned by the user manager, under `swarma-operator` authority and §3.2's phone or terminal path with exact-content confirmation and agent-session refusal; it must state plainly that the home's confidentiality is not guaranteed. Dispatcher cleanup has no retention authority and admits `delete` only (§4.3); the retention operation's unpublished format would need publication by the user manager (§16).

With keeper integration active, the dispatcher then revokes an identity only if its registration recorded it as one-shot (§14), as a separate, confirmed effect after account retirement. Standing identities are left to the operator. The allocation becomes `removed` only after its applicable cleanup effects are confirmed; executions become terminal only after their stop is confirmed and their allocation's cleanup obligations are recorded. The daemon's internal sweep (§7.2) owns ordinary allocation lifetimes while no request is running.

Standing allocations do not expire and are not retired on execution exit, provisioning failure or loss of caller authority. Only `swarma-operator` may retire or re-create them, with a signed operator record through §3.2's phone path (operator device key, biometric confirmation and exact content shown) or password-authenticated terminal fallback. Records originating inside an agent session MUST be refused. Once such retirement is authorized, the same confirmed cleanup effects apply; reconciliation may retry those authorized effects but cannot initiate retirement on its own. Account retirement never revokes a standing identity (§14). Re-creation is an operator decision, not an automatic recovery from an absent account or binding. The signed-record format remains unpublished (§16).

## 6. Holding and stopping

- **Supervisor.** The daemon owns the per-execution supervisor under `swarma-dispatcher`: new session, no controlling terminal, caller descriptors closed, bounded private logs of the executor's output in dispatcher state, durable registration before launch, and start/termination receipts recorded. User manager §7 owns the process **fate table** (R-FATE) beside R-FD3: one row per dispatcher daemon, supervisor, execution root/descendants, broker vendor-refresh child and session-host service, with unit/kill domain, stop/crash/restart fate, promised survival, death observation and maintenance affected set per platform/unit configuration. Dispatcher and host backends reference that table, not deployment defaults. Supervisor backend daemon loss follows the explicit `lost`/confirmed-stop path; there is no live supervisor adoption or second launch. Every supervisor write checks the durable daemon-instance epoch; an old surviving supervisor is fenced from journal/log/record writes. Reconcile its historical receipt/effect and stop it as required (§7); no extra wire epoch field is defined here.
- **Session-host output accounting.** When SH2+ takes output custody, the session host owns retained-output, queued-input and required-evidence byte/count budgets per session/principal and in aggregate (session-host §§3.1–3.4, 3.7 and its publication/qualification register). It reserves or charges bytes before durable acceptance and bounds runner transport buffers. Replacement or retirement never resets retained debt: required evidence stays charged until safe disposition. A hard control/journal reserve, sized for bounded admitted records and required stop, park, fence, reconciliation and audit transitions, is inaccessible to producer output. Admission refuses if the reserve cannot be maintained. Budget-boundary backpressure/refusal or an existing journaled park/stop path must remain bounded even for an uncooperative runner, preserving control capacity for affected and unrelated sessions; this adds no standing-session lifetime. Safe retention distinguishes disposable diagnostics from replay evidence: no deletion of required evidence to make room, no truncated transcript called intact, no absence inferred from missing evidence and no replay of unknown approvals/controls. Incomplete evidence retains closed/unknown state; storage corruption remains a storage failure. The existing supervisor output-size bound carries through the handoff (§§9, 12–13; §16 question 5); host publication and qualification precede activation.
- **Stop.** The ordinary receipt-backed stop is the helper's `exec.stop`, authorized for the dispatcher's own generations; the authenticated operator ALLSTOP path below can initiate receiver-journaled generation containment without a healthy dispatcher; ordinary ephemeral executions may also end through `user.retire`, which stops the account's processes before removal. Operator maintenance authority is explicit (§§8.1, 11). Stop and retirement share the user manager §4.7 account-wide scope and latest-receipt fence (§5.3). `idle` requires no account process; persistence-denial and quiet-period evidence are user-manager qualification prerequisites. Concurrent executions per generation would need exact per-execution containment before activation and must never fall back to session-only termination. Platform services and service managers end executions only through `exec.stop`, retirement or operator emergency stop; OS failures such as OOM are observed as `lost`, never successful cleanup. Qualification distinguishes caller disconnect/death, daemon death, executor ignoring SIGTERM and descendants escaping the session; a client connection is never the execution's lifetime authority.

**Node-wide operator stop (R-ALLSTOP).** One signed operator narrowing act through §3.2's phone path (authentication and one confirmation) or terminal fallback, refused from agent sessions. The operator command delivers the same act identity and canonical content directly to each service's operator intake; each verifies it and journals its part idempotently, independently of another service's reply. Per-service results are reported and undeliverable parts retried as unknown. The dispatcher's fail-closed hold is committed at its act admission, concurrently with fan-out, before forward admission and without waiting behind service calls. No offline writer of dispatcher state or writable hold file is authorized; a dispatcher-independent hold commit would need separate publication preserving exclusive ownership.

Issue user-manager range deny-all, broker freeze of all leases/renewals and session-host delivery closure plus bound-board snapshots promptly and independently. Start generation stops immediately after issuing those cuts with bounded parallelism; no stop waits for containment acknowledgements. Each part completes on its own durable evidence, and already-delivered tokens keep their vendor lifetime. An unavailable broker freeze reply cannot block helper stop progress; that broker part stays unknown and admission stays closed.

Before any generation is scanned, the user manager persists a root-owned ALLSTOP mark. Under the generation lock the launcher refuses every physical start while it is set, including materializers/exporters and already-issued dispatcher calls. The mark also closes generation creation and activation (`user.create`, helper-v1 `fw.apply` activation), or an authoritative closed-create frontier must cover the inventory. Account-process ingress and pending launch intents are fenced and reconciled before absence is final. A process scan alone cannot certify this frontier.

| ALLSTOP inventory member | Required outcome under the durable launch/create/ingress fence |
|---|---|
| Authoritatively never launched, complete generation-scoped launch coverage and no pending launch | Fresh qualified generation-bound zero-process observation recorded as this act's absence result. No invented execution, receipt or ordinary stop API. |
| Receipt-backed execution | Existing E-stop/latest-root-receipt interlock, account-wide termination scope and quiet-period confirmed absence. |
| Pending/ambiguous launch, missing/lost receipt history or contradictory process evidence | Reconcile original effects; retain obligations and claims. Missing history or an `idle` label never proves never launched. |

Unexpected processes in a receipt-free generation keep it pending for explicit operator reconciliation unless the joint contract publishes narrowly authorized generation containment under this act. Never signal an unfenced UID, reuse an old execution receipt, manufacture a dummy start, or automatically retire a standing account. The never-launched standing case is distinct from dispatcher-unavailable delivery even when both occur together.

The dispatcher initiates E-stops when available; the user manager journals termination as receiver. With the dispatcher absent, crash-looping, admission-unready or mid-swap, the authenticated terminal operator helper path initiates generation-scoped stops under the act; the phone-to-helper transition remains gated on publication and qualification. This is scoped operator emergency authority, not a widening of ordinary `exec.stop` callers. When the dispatcher returns it reconciles operator-initiated stops and its own hold/journal part, records operator-stopped outcomes (encoding unpublished), releases claims only on confirmed absence and never relaunches.

Direct containment and stops can progress without the dispatcher; whole-act completion and recovery require every durable part, including the dispatcher's reconciled part and fenced inventory coverage. Unknown/partial/refused parts keep admission closed. Explicit widening recovery requires authentication, exact-content confirmation and agent-session refusal; it names the stopped set and per-session restart scope, with successor authority durably suspended until expressly authorized recovery. Reopening clears the ALLSTOP closure only after all parts and ordinary readiness hold, with hold cleared last. Clearing maintenance, restore or another independent condition does not clear ALLSTOP, and clearing ALLSTOP does not waive other gates. Restart still requires the owner's lifecycle authorization or fresh admission; no automatic restart occurs. Act, receiver evidence, fence/frontier and recovery formats remain unpublished (§16); no new `dispatch-op/1` value is invented. Operator maintenance remains a distinct selected-stop act.

## 7. Reconciliation and the sweep

### 7.1 Reconciliation

Companion figure: [state-by-state reconciliation](../diagrams/reconcile.puml).

Runs at daemon start before forward readiness, periodically inside the daemon, and on `reconcile`. Establish exclusive ownership, compatible schema, journal replay and valid authentication/indexes before serving the recovery/control surface. Status/list, receiver observation, reconcile and already-authorised current-execution-bound stops remain reachable without a fresh launch grant when their particular evidence is sound. Classify every non-terminal record before forward admission. Retain unresolved records' generation/allocation, quota and capacity reservations; reject their forward effects. Unrelated work may proceed only if complete accounting and durable intent/claims demonstrably confine every possible unresolved result. Unbounded shared-state integrity, identity scope, accounting or authority keeps node-wide forward admission closed; maintenance, restore fencing and the fail-closed hold gate remain global barriers. Calls use §4.1's in-flight marker and unlocked I/O pattern, including observations and the sweep. Trusted binding/rebind rows below apply only where a binding is admissible; an untrusted workplace has no subscription binding, so no missing-binding repair is attempted. Workspace export obligations remain pending until complete-content custody or per-act operator waiver, including on expiry, failure, direct retirement and restore; a recorded result alone cannot discharge them. Reconcile each distinct materialize/work/export launch and its round linkage (§4.4). Cleanup consent permits bounded collection after ordinary expiry, never security-hold bypass or worker repair; unknown consent/launch/blob evidence retains the obligation (§3.4). Terminal refusal is immutable, and repair needs new current-authority admission/execution/effect (§5.2). For every allocation and execution that is not terminal, it compares the journal and effect table with the observations (§4.6), state by state:

| idle | binding known absent, ordinary allocation not expired or standing allocation | reconcile original bind/unbind observations; a new bind requires explicit fresh authority and `prepare` verdict, never automatic creation from effect absence; if authority is gone, retire only an ordinary allocation under §5.4 (expiry requires its elapsed gate); standing stays pending |
| running, claim `claimed` | supervisor registration conclusively absent | mark the claim `absent`; no launch happens later |
| running, claim `launching` | receipt unknown | keep waiting for the receipt or the launcher's answer; never relaunch |

| stopping | termination receipt missing / unfinished admitted stop | continue `exec.stop` under the same E-stop and identical canonical arguments; current-execution fence and account-wide absence remain mandatory |
| any record | supervisor survives a replaced daemon | reject its writes by daemon-instance epoch; reconcile historical receipt/effect and confirmed stop; never adopt it |

| workspace cleanup | interrupted/unknown export, missing/corrupt blobs or receipt | reconcile original launch/effect and complete-content custody; same-effect identical arguments only for unfinished export; no duplicate launch or deletion |

| workspace cleanup | complete-content receipt verified | discharge export obligation; retained content survives home deletion until authenticated import acknowledgement or authorized release |
| retiring / cleaning | effects pending | resolve workspace export obligation before helper `retiring`/home deletion; repeat applicable effects; terminal only when all are confirmed |

Reconciliation uses `effect.observe` rather than mutation solely to discover state: `recorded` maps by current target state; `rolled_back`/`not_recorded` are known absent for that effect only and never trigger automatic new create; `pending`/`unavailable` remain unknown; `contradictory` stays contradictory. Follow receiver-owned R-OUTCOME tables (§4.5) for create/launch/stop/retire and bind/unbind/replacement. Observe helper create/retire and broker bind/unbind/replacement, including retained removal/tombstone evidence. Launch/stop use qualified receipt and process evidence; observations do not waive confirmed process absence. After caller/grant expiry, read-only observation can resolve prior effects without renewing authority. Any forward admission requires fresh §3.4 checks; missing evidence keeps claims held.

Under ALLSTOP, restore or lost receipt history cannot certify no launch: retain unknown coverage until independently re-established, and require the fresh fenced absence result in §6.

Reconciliation of a standing allocation never initiates retirement or re-creation without the operator's signed record, including on a provisioning failure or known-absent account. It may resume already-authorised effects; unknown and contradictory observations remain pending. The absence of allocation expiry does not waive fresh forward-work authority checks; cleanup exporter authority is separately bounded by §3.4.

Helper retirement/recovery follows its bounded, dependency-based work contract (user manager §§4.4–4.6, 6–7). Serialized deletion batches yield its existing shared lock; an unrelated safely classified retirement need not finish before a stop/observation/launch on another generation. The dispatcher continues the original E-retire through cleanup/sweep retries, treats unfinished batches as `pending` under R-OUTCOME, retains UID/quota reservations and never declares `removed` before full deletion/account cleanup confirmation. Shared corruption or unbounded accounting still closes admission. This gives no new cleanup authority to the metadata-only daily root timer and promises no bound on a stuck kernel/storage device.

### 7.2 The sweep

The daemon runs an internal sweep every minute: reconciliation, ordinary allocation lifetimes, claim maintenance and log rotation. There is no external sweep timer or public sweep operation; caller `reconcile` remains scoped by §8.1. The sweep never expires standing allocations: they have neither `expires_at` nor a lifetime quota. It MUST NOT stop their executions for runtime, because they carry no `max_runtime` quota or runtime deadline. Ordinary executions retain §3.5's 4 h default and 12 h maximum; the sweep stops an ordinary execution whose runtime deadline has elapsed through confirmed `exec.stop` (§§5.3, 6). It reconciles standing allocations' authorized effects/executions and maintains claims and logs. Expiry-driven destructive cleanup follows §5.4's trusted-time and boot-inclusive monotonic elapsed gate. Persist elapsed/time evidence and classify clock incidents before authority evaluation or watermark advance. The sweep performs authorised renew-ahead E-rebind before the earliest credential window ends, only with consent and current renewed chains already supplied by §3.4's authorised principal; it cannot mint grants or reissue revoked/expired authority autonomously. Status reports each allocation's credential-authority horizon and the dispatcher grant's `--until` as the node-wide horizon, including approaching lapse; the status encoding remains unpublished. Unbind ends the old binding's running leases: until a fenced fresh-lease handoff is published and qualified for a holder, use explicit park/restart keeping the account; no seamless env-channel or app-server continuation is promised. Tokens already delivered keep their vendor lifetime. The sweep also progresses admitted cleanup exports within their consent and retained-content accounting, separately from forward work; security/identity/absence uncertainty stays held (§§3.4, 9). A sweep over many records uses bounded per-record scheduling and unlocked calls so one stalled receiver cannot block recovery controls (§4.1).

An absent daemon refuses; while forward admission is unready, the valid control surface reports ordinary lifetimes as unenforced/held and distinguishes standing allocations where expiry does not apply, elapsed-time holds and pending cleanup. Complete classification/confinement and accounting, rather than disappearance of every unknown, precede forward readiness (§7.1).

### 7.3 Usage watcher (R-WATCH)

The dispatcher consumes a read-only sampler's per-UID CPU, memory, process-count, home-disk, network and refused-connection counters (including mail ports) and applies per-admission-class thresholds. Use the recorded enforcement class and placement (§3.6), never circle membership as a substitute for either or as role/host-loop authority. The sampler has only the least privilege its OS requires, root only where required, and no other authority. Samples used for automatic action must bind the observed account generation, boot and sampling interval at collection; the current generation is revalidated against a stable ledger view before acting. Baselines and counter continuity never cross generations or boots; stale, unverifiable or reuse/reboot-spanning samples are discarded, never retargeted.

**v0 / S0a scope:** a hard threshold journals the reason and a current-execution `exec.stop` for the affected account only, with account-wide absence and retained claims on uncertainty; it sets the dispatcher's fail-closed admission hold to prevent further starts until explicit operator recovery. No unjournaled kill, unrelated-account stop or automatic node-wide ALLSTOP is authorized. Follow user manager §7 R-FATE and R-OUTCOME stop continuation. v0 offers stop, hold and status only: no per-account egress-freeze guarantee, token retraction or phone notification. The node-wide range deny-all is never substituted for a one-account freeze.

The alert phase is explicitly status-only: the threshold reason, journaled stop progress/confirmed absence and hold are visible when the operator reads status through `swarma-observer`. Containment never waits for notification delivery or its availability. Any future notification lane is separate from operator mutation authority and must publish an owner, bounded qualified route, durable delivery/status, unavailable-channel and retry behavior, closed content and rate bounds before it is promised. It gives neither the watcher nor the dispatcher new egress.

**v1 / S2 open contract:** per-account egress-freeze dominance over stale re-apply, ordered narrowing/release, explicit authorized release separate from restart, versioned effects and helper `fw.apply`/`fw.remove` R-OUTCOME tables remain open for that contract package. Independent stop progress, kernel/proxy-session reconciliation and freeze/recovery qualification must be published there; this wave does not specify the lifecycle. Thresholds, sampler/provenance, status and future alert encodings remain unpublished (§16 question 27).

| `host_stop` (gated §12) | targets an execution under the session-scoped host admission permit; request/reference/authentication member format unpublished | only the configured session-host principal; journaled E-stop, host-requested, distinct from owner `cancel`; no start authority |

Operator records for `team/1`, standing retirement/re-creation, maintenance stop authority, standing re-grants, trusted-circle admission, R-TRANSFER export waiver, R-CEILINGS soft-row acceptance, R-ALLSTOP and its explicit recovery follow §3.2's phone or terminal custody/confirmation contract and MUST be refused when originating inside an agent session. They remain distinct from ordinary caller-request `auth`; their transport, canonical signature and refusal mappings would need publication (§16). `swarma-observer` is read-only: it can read dispatcher state (status, grants, accounts, bindings) without confirmation and cannot `cancel`, `retire`, `reconcile`, `drain`, renew authority or invoke bring-up. Grant/account/binding read representations beyond the existing status/list schema would need publication; no operation or member is added here.

E-rebind is the authorised renewal effect on an existing allocation (§3.4); its request/transport and broker binding-replacement grammar are unpublished. This does not invent a `dispatch-op/1` operation value. `network?` is checked against the machine-owned binding at `prepare`, never accepted as authority. Status reports credential horizons, unresolved effect/cleanup obligations and forward-admission closure separately from control availability; added representation details would need publication (§16).

For an ordinary allocation, omitted `max_runtime` uses §3.5's 4 h default; a supplied value is subject to the 12 h maximum and configured quotas. For a standing allocation, `max_runtime` MUST be absent; supplying it MUST be refused before launch, never used to install a deadline or silently ignored. The refusal-code mapping is unpublished (§16, question 8); no new code is asserted here. Allocation designation, not the requested duration, determines which policy applies.

### 8.2 Results

`dispatch-result/1` (CCJ-1 canonical JSON): `{ v: 1, request_id, ok: true, result: { … record … } }` or `{ v: 1, request_id, ok: false, error: { code, message, stage? } }`. A repeat of a completed request returns the stored result with the record's **current** state. The meaning of terminal outcomes is fixed: `exit` (the harness ended), `failed` (a stage failed and cleanup is confirmed), `cancelled`, `expired` (ordinary allocation lifetime or ordinary execution runtime; neither applies to standing allocations or their executions), `lost` (the holder vanished and the execution was stopped and confirmed absent).

Workspace collection after ordinary expiry is only the bounded cleanup consent in §3.4 through existing launch/effect machinery; it adds no operation or member. Same-workspace repair remains separately admitted forward work (§5.2). Status must distinguish accepted result from complete-content custody, refusal/typed permission failure, unknown export, waived obligation and retained-content release progress; representations remain unpublished (§16 question 22). Observer status cannot release workspace content.

Workspace exports use the separate DRAFT `swarma-dispatcher workspace-result/1` object (§5.2.1), including refused exports with no partial entries. Its schema does not publish a new `dispatch-op/1` operation or transport.

### 8.3 Socket `dispatch/1`

Companion figure: [service daemon and gated SH2+ backend](../diagrams/v1-daemon.puml).

The daemon `swarma-dispatcher` runs as `swarma-dispatcher` and listens in `/opt/swarma/run/dispatcher/`. Its byte framing is defined completely in [the byte-frame contract](frame.md): a four-byte unsigned big-endian payload length, 1..131072 payload bytes inclusive (128 KiB), with a separate four-byte prefix and a 131076-byte maximum wire frame. Empty or over-limit payload lengths refuse before payload allocation/read; clean EOF and truncation are distinguished there. Broker §4.1 and §13 supply the additional connection rules; the dispatcher payload cap is 128 KiB (§10). This is the service transport from slice 0, including the Curator CLI client. The broker rules include peer authentication, server-UID verification, protected endpoint/connection lifecycle and descriptor restrictions; descriptors are not a request transport. An absent daemon or authentication, permission, version or malformed-response failure refuses with no command fallback. Admission-unready is separate from control availability: after exclusive ownership, compatible schema, journal replay and valid authentication/indexes, the existing socket serves authorized recovery controls (§§7.1, 11). Forward readiness requires complete classification and safely bounded accounting; no alternate service or launch path is introduced. Later capabilities reuse this transport; queueing/events/long waits are omitted initially. After an ambiguous reply the client repeats the same request with the same `request_id` and signature.

| Operation class on the existing socket | During recovery / closed forward admission |
|---|---|
| own status/list/capacity, dispatcher reads by `swarma-observer` without confirmation, and receiver read-only observation through reconciliation | reachable after control prerequisites; expose unknown/held accounting honestly, no new launch grant |
| reconcile and already-authorised current-execution-bound `cancel`, `host_stop` or selected operator stop | reachable only with sound particular identity/authority; record intent promptly, unknown launch still waits for its receipt |
| bounded cleanup exporter admission through existing machinery | only with §3.4 retained consent, sound identity/absence, capacity and security fences; no ordinary expiry renewal, no bypass of maintenance/restore/hold/time barriers; format unpublished |
| provision/start/dispatch, `host_start` successors, E-rebind and other authority-creating work | require forward readiness, fresh authority/verdict and no record-local uncertainty; maintenance/restore/hold/time barriers still close them |

Receiver `effect.observe` remains the existing helper/broker API, not an invented dispatcher `observe` operation. Unsupported gated operations remain disabled.

### 8.4 Relation to the platform launch contract

The dispatcher implements a **local headless subset** of `dispatch(LaunchRequest)` (architecture §7.1, §5.1): it starts already composed plans; it records the opaque provenance (`board_ref`, `parent`) whole; it refuses interactive transport, native resume, seeded continuity and remote targets (`unsupported_combination`). Interactive executions under agent accounts arrive with the session host's platform phase (its backend gate, §12), not in this dispatcher (owner decision 2026-10-10); goals are optional. For now only the launching caller at start (through the launcher), or the board/orchestrator for board goals, authors a session goal (D-GOALS); an agent account has no goal capability on the session-host socket. This keeps authorship with the initiating caller while a separate agent namespace and its authority bounds await SH2+ design. The host must function without goals, a board, an orchestrator or their toolchain; board goals are an optional client of a generic goal interface. Choosing self-goals in a separate namespace versus caller/board-only authorship remains deferred (§16). A versioned LCH adapter, owned with the launch client, composes plans, compares pins and maps `LaunchRequest` onto these operations; until it exists, nothing claims full LCH conformance.

**Workplace backend (R-WORKPLACE; gated).** `workplace` is the project-side home/account allocation class of a remote worker. `swarma-rb-exec` runs under a service principal, never the workplace UID; policy, caps, durable effect claims, audit and certificate renewal control stay outside the worker's UID. Every workplace is untrusted-class unless an operator act admits its remote worker to the trusted circle (§3.6). Every workplace still has zero egress with no proxy destination or loopback, and never has a subscription binding/lease or host-local agent loop; trusted-circle membership enables only donor-side opt-ins. A remote workplace requires enforced networking; it is admissible only after helper v1 on that host, with applied-state and loopback qualification (user manager §8). The helper owns the fixed SSH relay-stub account shape; dispatcher/host/broker sockets refuse workplace principals without configured roles. Host-local workplace jobs require a new qualified backend, not support inferred from the current remote-target refusal. Their wire names `swarma-rb/1` and `swarma-workplace-exec/1` stay unpublished (§§12, 14, 16).

## 9. Capacity

Figure M-DP2: [capacity ownership alongside allocation and execution claims](../diagrams/agent-claim-states.puml).

| Admission condition | Initial slice | Later queue capability |
|---|---|---|
| temporary capacity gate closed | refuse with `capacity:*` | queue with a durable handle; re-check authority and gates before starting |
| quota exceeded | refuse `quota_exceeded` | refuse `quota_exceeded`; never queue |
| authority invalid | refuse | refuse; never queue |

- **Claims.** A capacity claim is a durable record `{ claim_id, owner record, class, resources, expires_at }`, taken at `capacity`, transferred to the execution at `start`, released after confirmed end/absence, including cancel, expiry and reconciliation; unknown process evidence never releases it. Re-checks before the launch exclude the claim's own resources, so an admitted request never refuses itself.
- **Counters.** Allocations and executions are counted separately, per caller and in total. Refused rounds retain home, UID and live-allocation quota; confirmed absence releases the work execution slot, not the export obligation. Reserve or retain bounded cleanup capacity and schedule its progress alongside forward work, without exempting actual resource/storage safety, execution claims or security fences. Account retained result/blob custody independently, including when the caller is unavailable or the home is deleted; reservation/accounting/scheduling encodings and bounds remain unpublished (§16 question 22).
- **Host-retained output.** Session-host accounting (§6; session-host §§3.1–3.4, 3.7) separately reserves/charges producer-induced service storage per session/principal and in aggregate, including queued input and required evidence. Retained debt survives replacement/retirement until safe disposition; account home quotas and admission free-space checks do not discharge it. Reject admission when protected control/journal capacity cannot be maintained; producer exhaustion cannot spend that reserve. Bounds, reservation and retention formats remain host-owned publication work (§16 question 5).
- **Authority at admission.** Ordinary forward prepare and every work start require a fresh `revocation.check` with the matching `prepare` or `start` context (§3.4); `revoked`/`unavailable` refuse before new effects, including broker restore fencing. Dequeue requires its own `dequeue` check, never a saved prepare verdict. Broker final checks remain independent and mandatory. Cleanup exporter starts use the separately admitted bounded consent in §3.4 with fresh revocation/security-case evidence, never ordinary worker authority or a lease.
- **Gates** (architecture §5.1.4): `slots`; `disk` on every volume the run touches (agents root, dispatcher state, broker store and admitted content-custody destination); `cpu_idle` over a window; `hold` (host-wide, read fail-closed: unreadable means held). ALLSTOP closure is independent of maintenance/restore/time gates and clears only through §6 explicit recovery after every service part, including dispatcher reconciliation, is known; receiver fences also reject starts already issued before hold. The initial slice admits `agent-headless` for the trusted class. `agent-headless-build` is withdrawn for agent accounts (R-EXEC); its build-lock and syspolicyd gates are removed. Builds/tests are only R-VERIFY off-host work, not a dispatcher job class here. Class/capability, exec-profile and egress failures are admission refusals, never temporary capacity queueing.
- **Queue (later capability).** Temporary gate closures queue a request with a handle; permanent refusals (quota, authority) never queue. The queue is bounded per caller and in total, fair across callers (round-robin by caller), durable, and re-checks principal, signature/window, quota, every gate and a fresh `revocation.check` with context `dequeue` at dequeue. `drain` either parks queued requests or rejects them, as the operator chooses.

Unresolved in-flight or restored work counts conservatively against quota/capacity; claim expiry is not absence. Forward admission of unrelated records requires §7.1 confinement and complete accounting. Unbounded accounting/shared integrity closes the node; bounded record-local uncertainty retains only its own claims. Recovery controls remain available under §8.3 prerequisites.

### 9.1 Host capability matrix (R-CEILINGS)

Each host publishes a qualified matrix per OS release for CPU, memory, process count, IO, disk, temporary areas, process visibility and network, marking each ceiling hard (kernel-enforced), soft (watcher-enforced) or absent. Admission classes declare minimums; the dispatcher admits a class only when that host's matrix meets them. No OS is excluded by name, including macOS. The untrusted minimums are hard process-count limits, enforced zero or provider-only egress (workplaces always zero), an exec profile, isolated temporary areas, and hard memory/CPU/disk ceilings where the host provides them. Whether soft rows can substitute on a host lacking hard ones remains an open owner decision, recorded per host by an operator act; no implicit fallback is admitted.

The Linux reference selects the root-created, non-delegated per-execution unit from R-FATE for agent/workplace executions: CPU, memory, task and IO limits; private temporary directory, no new privileges, read-only system; per-UID disk quota on the agents filesystem; `KillUserProcesses=yes`, `/proc` with `hidepid=2`; the R-EXEC allowlist; R-NET-TOOL network namespace/address families; and a per-execution CPU-time budget. For Linux hosts admitting untrusted work, host infrastructure disables unprivileged user namespaces, io_uring and unprivileged eBPF, sets `kernel.yama.ptrace_scope=2` and patches sudo promptly; the platform verifies those baseline rows.

The macOS reference is a sandbox profile for exec/files/network, per-user process-count and per-process CPU limits, background scheduling to throttle CPU/IO, an aggregate APFS agents-root volume quota, and soft watcher limits for memory/per-account disk. Qualification records the known gaps: no public hard per-account memory ceiling, no per-user APFS disk quota, and the deprecated sandbox-profile interface. Soft/absent rows do not exclude macOS; admission follows the matrix and any explicit owner decision. Matrix/class-minimum formats, numeric ceilings and qualification evidence would need publication (§16).

## 11. Installation and activation

Companion figure: [service activation and bounded maintenance](../diagrams/activation.puml).

- **Operator prerequisites (R-OPERATOR).** Establish protected `swarma-operator` (no harness sessions), its broker operator/account-owner and user-manager `operator` roles, and mandatory read-only `swarma-observer` before operator acts are admitted. For the phone path, configure §3.2's pinned operator device key, SSH-over-tailnet key-only login and forced operator command with no shell. Install the password-authenticated terminal fallback (`timestamp_timeout=0`, no `NOPASSWD`). The terminal path works without a phone; no additional hardware or signature-algorithm change is mandated. Never restore operator signing authority into an account that hosts agent sessions. Key enrolment, rotation and phone loss remain open (§16), with terminal re-enrolment proposed.
- **Installation.** The installer creates `swarma-dispatcher` with the helper, places the binary in `/opt/swarma/libexec/`, writes only dispatcher-to-helper/launcher no-argument sudo rules, registers the service principal in helper policy and broker configuration, generates its key, and obtains the operator-issued constructible dispatcher grant (§3.4). It installs the daemon and protected Unix socket using the broker's service/connection rules. It requires an authenticated or operator-controlled time source (for example NTS) and the common time-confidence/monotonic-expiry policy (§§3.4, 5.4). With service-profile v1 enabled, it installs and verifies dispatcher deny-all egress under user manager §8, including DNS/resolver denial (§13). There is no caller-to-dispatcher sudo rule, detached-command bootstrap, external sweep timer or command-to-daemon conversion.
- **Readiness.** Verify the R-RANGE-DENY range rule/probe, host capability matrix, R-EXEC profiles and declared socket reachability; a host admitting untrusted work must meet R-SHARED (§§9.1, 13). Start with admission closed, take exclusive state ownership, validate state reader/writer compatibility, replay the journal and reconcile effects, receipts and process evidence. Publish control availability once exclusive ownership, schema compatibility, replay and authentication/indexes are sound. Publish forward readiness after every record is classified and complete accounting confines unresolved effects to retained identities/claims (§7.1). Record-local unknown/contradictory evidence blocks that record; unbounded shared uncertainty blocks the node. Authorized observation/status/reconcile/stop remains reachable under §8.3. An absent service refuses ordinary dispatcher operations without fallback; direct operator ALLSTOP containment/stops still progress under §6, with the dispatcher part unknown until reconciled.
- **Emergency stop (R-ALLSTOP).** Install the operator-only node-wide stop and explicit recovery path (§6). Direct fan-out, prompt independent cuts/stops, receiver launch/create/ingress fencing and §6's distinct never-launched/receipt-backed/unknown inventory outcomes are installation/qualification prerequisites. Hold, generation absence, user-manager range deny-all, broker freeze and host delivery closure/board snapshots remain separate journaled parts, including when the dispatcher is unavailable. Partial/unknown results keep admission closed; recovery requires an explicit widening operator act with authentication plus exact-content confirmation and agent-session refusal, never automatic restart. Act/record formats remain unpublished.
- **Bounded maintenance attempt (R-MAINT).** Before a backend-mode change, mutable-state migration or binary swap: (1) close new admission; (2) durably inventory existing executions and selected stops; (3) require a signed selected-stop operator record under `swarma-operator` authority via §3.2's phone path (operator device key, biometric confirmation, exact content shown) or terminal fallback, with authentication and exact-content confirmation; refuse records originating inside agent sessions before any selected stop through the dispatcher and journaled helper `exec.stop`; (4) require confirmed process absence and reconciliation for all affected executions before changing mode/state/binary; the affected set is defined by the user manager §7 R-FATE table for the exact platform/unit configuration, never guessed from process parentage. Closing admission or draining queued requests does not stop a running execution. The maintenance deadline bounds this attempt, never a standing execution's lifetime. Unknown/refused stop, uncertain absence, incomplete reconciliation or deadline exhaustion defers maintenance with admission closed; no swap or migration is permitted. Progress and unresolved obligations remain durable for operator review and resumption using the same stop effects/receipts.
- **Retention and restart.** Maintenance keeps standing allocations and identities; it performs no automatic retirement, re-creation, live adoption or lifetime expiry. Persist intended restarts for operator review; a restart needs fresh authority, fresh `prepare`/`start` verdicts and an admitted plan/transport. Unsupported rows stay visibly stopped. Native resume is only available after its §12 gate; maintenance promises no seamless context continuation.
- **Cutover and rollback.** After confirmed absence/reconciliation, take exclusive state ownership, validate/migrate the schema and activate the selected binary/backend. Repeat recovery before publishing readiness. Rollback follows the same fenced absence and compatibility order, retains later durable records and never restores an old snapshot as a repair. A binary refuses unreadable or unsupported state; no live supervisor adoption is allowed. Maintenance authorization, deadline/progress and restart-review formats remain unpublished (§16); their wire fields/codes are not invented here.

### 11.1 State loss and restore (R-GEN)

State loss, unreadable state or a declared restore is distinct from ordinary crash replay. Keep node-wide forward admission fenced. Before restored bytes become visible, an operator establishes a restore mark/fence outside the restored failure domain, reusing the broker's fail-closed restore procedure (§15.4). A user-manager ledger restore closes every direct ledger consumer (dispatcher, broker, launcher, session host), not only `effect.observe`. The dispatcher records the highest ledger store epoch seen and refuses a lower one pending operator reconciliation; its floor is useful only if surviving outside the restored domain and cannot certify a whole-machine rollback. The fence/epoch/control-recovery formats would need joint publication (§16).

Restore or reconstruct private dispatcher state while ownership is exclusive. Treat pre-restore receiver coverage as `unavailable`, never `not_recorded`, until independently re-established against OS directory inventory, surviving root receipts/audit, broker tombstones, other component records and operator evidence. A restored snapshot cannot certify its own completeness. A generation seen `retiring`/`removed` in surviving evidence never returns `active`; an active ledger record with no OS account is contradictory, not creation to resume. Fresh generations reference user manager §4.1's random 128-bit allocator; old restored identities are not authenticated by randomness.

ALLSTOP closure survives restore: reconcile receiver fences/frontier and independent launch history before classifying a generation as never launched; no snapshot supplies its own fresh absence certificate (§6).

Reconcile both directions: existing dispatcher records, user-manager accounts with `created_by` equal to this dispatcher, its broker bindings and surviving receipts. Report unmatched objects as orphans, hold their identities and conservative quota/capacity obligations, and require an explicit operator-signed decision under §3.2's custody contract to retire or re-adopt their records. Names/UIDs alone authorise neither deletion nor adoption; no automatic orphan or live-supervisor adoption is allowed. Re-adoption does not create fresh mutation/launch authority or reactivate a retiring generation. Inventory and decision formats would need publication (§16).

If the ledger was also rolled back, recover post-snapshot objects from OS inventory, preserved receipts and operator evidence; lost evidence means coverage is unknown and bounded recovery is not promised. An undeclared internally consistent whole-machine rollback is not locally detectable. Reopen forward admission only after the external fence is reconciled, coverage and non-resurrection are established, and §7.1 classification/accounting holds. Safe recovery controls may be served under §8.3 while forward admission stays fenced.

## 12. Session-host backend (later; activation gate)

Companion figure: [backend process identities, host admission and recovery](../diagrams/v1-daemon.puml).

Before the SH2+ session-host module may hold executions through its agent-side runner (not the service UID):

- **Owner admission (R-SESSION).** The owner's admitted `start` explicitly carries session lifecycle authorisation when successors are allowed (§§3.4, 4.2). Same allocation/generation, stored plan verbatim and owner's grant window bound it; ordinary allocation lifetime and cumulative/anchored restart budget also bound it. A one-start request admits only that start. The original caller ancestry stays the broker dependency; the host never obtains a caller chain.
- **Session permit and physical start (R-START / R-SESSION).** The durable **host admission permit** is session-scoped for one `logical_session_id`. Only the configured session-host principal invokes `host_start`, carrying `(logical_session_id, execution_id, controller_epoch, op_id)` and referring to that permit. Every physical start has its own claim, epoch/fence, distinct E-launch and root-receipt interlock. The host first persists intent with delivery closed. Dispatcher alone calls `swarma-user-launcher`; the host has no launcher sudo authority, helper host role or delegated root start authority.
- **Host stop.** Only the configured session-host principal may invoke `host_stop` for an execution under its permit. It uses the journaled E-stop path, user-manager `exec.stop` single account-wide scope and confirmed absence (§§4.5, 5.3, 6); it is durably host-requested, distinct from owner `cancel`, and confers no start authority. Unknown launch/stop evidence retains claims and waits for the same effect/receipt; old execution receipts cannot stop successors.
- **Cancellation and withdrawal.** Owner `cancel` or `retire`, revocation/expiry of the owner's chain, an operator-signed standing-retirement record or R-MAINT durably withdraws successor authority; R-ALLSTOP durably suspends it until explicit recovery names the stopped set and restart scope (§6), serialised with admission under the state lock; no autonomous repeat follows cancellation. Unknown permit state closes successor starts. Cancellation before call issue prevents the call; after issue, resolve the same effect/root receipt and stop if required, never launch twice. Host failure keeps claims and delivery closed until reconciliation. Publication would need the authenticated withdrawal call/encoding; no new operation value is invented here.
- **Fences without cross-service locks (R-LOCK).** The host owns durable per-session fences and validates its current epoch locally; it holds no fence/state lock across `host_start` or `host_stop`. Dispatcher validates the submitted four values at each effect under its local lock, marks the record in flight, then releases it for receiver I/O. A mid-call host fence change requests withdrawal through a second call. The post-call handler rechecks epochs/fences; stale results cannot open delivery (§4.1). Atomicity is per effect at the receiver, never a cross-service lock. Controller-only re-adoption keeps `execution_id` and needs no permit action; execution replacement uses a new ID under the successor rules below. This permits no live supervisor adoption in dispatcher maintenance.
- **Registration before delivery.** The approved agent-side runner opens a fresh authenticated host channel. Current-controller-epoch registration and readiness precede delivery; a closed fence or stale epoch refuses delivery. The runner checks the exclusive native-session lock (session-host §3.4).
- **Ownership and fate (R-FATE).** Dispatcher owns admission, privileged physical starts, records, stop and cleanup; host service owns metadata, logs, receipts, fences and input admission; agent-UID `swarma-session-runner` owns PTY/app-server transport and credential renewal. Account generation, execution claim epoch, daemon-instance epoch and controller epoch are distinct. User manager §7's fate table defines exact platform/unit survival and maintenance affected sets; no survival is inferred from `setsid` or UID changes. Host/runner is a later qualified consumer; host service embeds no broker client. Every handoff is published before activation.
- **Output/storage handoff.** The session host owns the accounting in §6 and its §§3.1–3.4, 3.7: preserve dispatcher output-size bounds, producer and aggregate retained debt across replacement/retirement, bounded buffers/refusal and protected control/evidence capacity. Before SH2+ activation, qualify sustained runner output and closed-fence queues at budget boundaries, replacement attempts to evade debt, evidence-retention floors, affected/unrelated-session control capacity and aggregate exhaustion refusing new work without reserve consumption or unbounded refusal logging. Storage location, budget values and retention/compaction/failure formats remain unpublished (§16 question 5).
- **Publication gate (I4).** The session lifecycle authorisation member and ordinary restart-budget format, session-scoped permit/reference, `host_start`/`host_stop` authentication, host-requested record representation, withdrawal durability, per-use replay/claim/crash ordering, root/host receipts and ownership handoffs would need joint publication and qualification (§16). No tickets exist. Naming the semantics does not publish unspecified wire members, values or refusal codes; the backend stays disabled.
- **Native resume (D-RESUME; later backend only).** On the same machine, a non-breaking harness version change is allowed by semver: same major, and for 0.x the same minor, without an extra qualification row. A different major or 0.x minor refuses. Retain the same runtime family, managed home, profile pin, transcript integrity, exclusive native-session lock, ready authentication and current grants. A harness resume failure is reported as `resume-failed` for the caller to decide; no automatic fallback or portable seed is part of resume. A per-harness note records vendors known not to follow semver. This does not enable resume in the current local headless subset (§8.4).

| Successor `host_start` admission | Required behavior |
|---|---|
| owner lifecycle consent absent / replay of one-start request | no successor; fresh checks cannot substitute for consent |
| repeated `(logical_session_id, op_id)`, including after host/dispatcher crash | return the same recorded successor and effects, never create a second; changed intent conflicts under existing replay rules |
| previous execution claim not confirmed absent | refuse `agent_busy`; unknown is not absence |
| plan, profile pin or posture diverges | new owner admission required; host supplies no replacement plan bytes |
| owner principal retired/inactive, chain expired/revoked, or fresh `revocation.check(start)` unavailable | no physical start; original ancestry remains mandatory |
| ordinary lifetime or cumulative/anchored restart budget exhausted | no successor; restarting never extends lifetime or resets runtime windows |
| valid consent, current owner/chain/window, fresh start verdict, confirmed absence, unchanged plan and current fence | new execution claim and distinct effects under the session permit; standing runtime stays unlimited |
| controller-only re-adoption | same execution ID, no physical start or permit action; host delivery fence still applies |

The permit does not choose the reboot requester. The host or project registry remains an open publication choice (§16); whichever is configured acts only within the owner's session lifecycle authorisation.

**Workplace gate (R-WORKPLACE).** A workplace is a separate project-side allocation/backend (§8.4), not an agent-account session backend enabled by SH2+. `swarma-rb-exec` is service-owned; workplace jobs use the dispatcher-owned launcher, root receipt and `exec.stop` path under the workplace UID. Before enabling it, publish one-job-per-execution versus a standing workplace-runner shape, concurrency/blast radius and current-execution fencing. In the runner shape, per-job process-group cancel is best effort; unconfirmed descendants require account-wide runner stop, retained unknown job claims and no effect replay, then freshly admitted runner restart. Publish service-principal policy/effect/audit custody, fixed SSH relay entry, user-CA custody, enforced-network/applied-state and loopback evidence. The OS confines the account writable set and R-EXEC profile; R-TRANSFER separately records the task write scope for export/import. Workplace egress is zero, qualified with the Linux network namespace without external interfaces plus Unix-only address families, or the macOS network-denying sandbox plus per-UID deny. Both mechanisms require qualification. No subscription binding or host-local agent loop is allowed. `swarma-rb/1` and `swarma-workplace-exec/1` remain unpublished and workplaces stay disabled until these gates hold.

## 13. Security

- Unprivileged; its powers are its helper role (its own agents), its broker role (their bindings), the launcher rule, the stop operation, and its key, which signs leaves only inside its own grant.
- Callers are authenticated by the kernel and by request signatures; plans are opaque; the dispatcher never reads Curator fragments or credentials.
- An agent that compromises its own account cannot reach the dispatcher's state, key or sudo rules; it can call the dispatcher only as a caller with its own grant.
- **Service egress (R-SVC-EGRESS).** Dispatcher has none: deny-all, including loopback TCP, under user manager §8's v1 service-profile rows; Unix-socket IPC remains usable. No local DNS is needed. Resolver denial (including Mach/XPC paths on macOS and resolver sockets on Linux) must be separately qualified; per-UID packet rules alone are not DNS evidence. Verify the row and parent anchor at every service start and on the published helper-owned schedule. A missing row/enforcement lapse raises an incident and drops forward readiness; safe recovery controls and process response follow §§7.1, 8.3 and R-FATE. Periodic checks have a detection window and do not promise continuous enforcement. This v1 capability does not claim slice-0 kernel containment or disable the software-root slice; formats, schedule/owner and per-OS evidence would need publication (§16).
- **Watcher alerts (R-WATCH).** v0 is status-only through `swarma-observer` (§7.3), with no phone-delivery promise and no new egress allowance. Future notification authority is distinct from signed operator mutation authority; delivery failure never delays containment.
- Logs: the supervisor backend stores executor output with size bounds in dispatcher state; the SH2+ handoff retains that invariant under session-host-owned producer/aggregate accounting, retained debt and protected control/evidence reserve (§§6, 9, 12; §16 question 5). The qualification scans these logs, the executor and broker artifacts for credential material; the trusted boundary is the executor and the harness release it qualified (broker §12.2).
- The audit log records each request, decision, effect and cleanup as typed metadata.

**Internet tools (R-NET-TOOL).** Internet is a tool of the agent loop, never general network access of the account. The design works without web access: by default the donor loop reaches only its model-provider endpoints and our host, and our environment has no internet. No search/fetch tool is offered by default; CIP-0008 lockdown keeps provider-side search disabled and no donor-side web server runs. Tasks carry the necessary resources read-only next to the workspace, with their digests in the plan (§5.2); they are data, never instructions. A worker requests more by ordinary letter or outcome and never fetches. The trusted side fetches, checks and attaches. Resource caps and formats remain unpublished.

The trusted circle is our own agents plus remote workers admitted by an operator act at admission. Web search is supported as an explicit per-identity opt-in for that circle only, never for the untrusted class. Membership enables donor-side opt-ins only and never changes any host boundary, reviewer eligibility or host-loop eligibility; positive role/class/placement predicates still apply (§3.6), including to circle-admitted remote workplaces. Three design options have unpublished formats:

- **Provider-side search:** a qualified tuple proves server-executed search runs at the provider with no local fetch; remote workers need a CIP-0008 tuple change.
- **Donor-side platform-shipped MCP server `swarma-web`:** its own donor-side identity in variant B, or its own sandbox profile in variant C; never the harness identity (whose egress remains the provider allowlist only) or bridge identity. Its egress is search-provider API endpoints only. It holds the donor's own search key in that identity, or in the donor's Keychain or a 0600 file in variant A. The key never crosses the channel, appears in a `swarma-rb/1` frame/package or can be requested by the project. Donor consent occurs at `init`; it never fetches arbitrary URLs from the donor address. Results reach only the donor model as tool results.
- **Local-agent platform web service:** reached over a Unix socket, with its key in a service account, never an agent account, and an allowlist, rate limits and logs. The opt-in adds no internet access to the local agent account.

For remote workplaces only the admitted SSH connection exists on our side. Dependencies download only in R-VERIFY runners. No `direct` or `external-http-proxy` can be bound to any account on a platform host, trusted or untrusted; these and cooperative profiles remain for operator machines without the platform only (§3.4). The model-provider proxy and runner dependency-egress profiles require host/port allowlists with no mail ports, private/metadata dial guards, per-identity rate/connection/daily-volume caps and logs. RWP's egress service is a candidate implementation. Network-profiles N15's revision of 2026-10-13 owns the listener contract: one listener per `account_generation` bound to `profile_ref`, only that account's own port admitted, with `served_policy_digest` and `service_generation` evidence (§3.4). This spec references those requirements, never specifies N15's formats.

**Static range rule (R-RANGE-DENY).** From v0, before any account exists, the installer places a static default deny for agent/workplace UIDs 30000–59999 in the helper-owned parent anchor/table, independent of per-account `fw.apply`. It admits only platform proxy listeners; v1 narrows each account to its bound profile or zero egress. The untrusted class requires v1. Linux uses nftables `meta skuid` range rules covering every protocol with counters/logs. macOS uses pf `user` range rules and launcher-applied sandboxing for traffic beyond TCP/UDP. Qualification proves that no earlier `quick` rule in any anchor (including ingress) can match range traffic on any interface, including loopback/tunnels. A dedicated test UID runs an active precedence probe at install, every service start and the verification schedule; a failed probe is an incident and drops enforced readiness. Dispatcher admission consumes that evidence, never a claimed profile alone.

**Socket and deployment rows (R-SOCKETS / R-SHARED).** Qualification probes from a test UID that reachable Unix-domain sockets equal the declared platform set: container-runtime sockets, tailnet daemon, other users' session daemons and all undeclared sockets are unreachable. A host admitting the untrusted class runs no shared services: no message server, ingress/reverse proxy, media server or operator session daemon. Platform services themselves are not shared services. These are host qualification/deployment rows checked at admission, not an OS-name ban.
